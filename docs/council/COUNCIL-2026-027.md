# COUNCIL-2026-027 — Public Course Catalog / Unauthenticated Preview Pages

**Date:** 2026-09-20
**Status:** Ratified
**Author:** Platform review (context: Council Review 3, Agent 4 — `docs/reviews/2026-09-19-council-review-3-synthesis.md` — ranked this the #2 competitive gap, right behind auto-enrollment on registration, COUNCIL-2026-026, shipped as v0.30.0)

---

## Context

Every course page in ChurchCore LMS requires authentication. `middleware.ts` redirects any unauthenticated visitor away from every route except `/login`, `/auth`, `/join`, and `/api/`. This means a church has no way to use the LMS as an outreach tool — there is no way to let a prospective member browse "our free Bible study" before creating an account. Every consumer LMS ChurchCore competes with (Teachable, Thinkific) treats a public course catalog as table stakes.

A directly analogous unauthenticated surface already exists and was verified as the pattern to extend: `/join/[slug]/page.tsx` looks up an organization by `slug` via `createServiceClient()` and renders public org branding to a visitor with no session — including an already-shipped anon RLS policy, `"organizations: anon read active"` (`supabase/migrations/20260620200800_handle_new_user_org_id.sql`), that this feature's own anon policies are modeled on.

**A critical, independently-verified finding surfaced during spec review**: migration `20260914154000_restore_anon_table_read_privileges.sql` granted `GRANT SELECT ON ALL TABLES IN SCHEMA public TO anon` (plus a matching default-privileges clause), and this was confirmed by reading the migration directly. This means RLS is *currently the only gate* on every table for the `anon` role — a new RLS policy alone would be enough to make a course's row visible, but would not by itself prevent a direct PostgREST call from requesting the `content` column (where quiz answers, assignment prompts, and discussion posts live) on any row that policy allows. Row-level security and column-level grants must both be tightened for this feature; RLS alone is not sufficient here, which is different from every other anon-facing surface shipped so far in this codebase.

**A second, more severe pre-existing bug was discovered and fixed during backend implementation (Prompt A.1 below), independently reproduced against a real Postgres instance**: `organizations` and `org_members` both still carry self-referential RLS policies dating to the original `20240601000002_canvas_block_model.sql` migration, written before `profile_roles` existed as the RLS hot-path table (CLAUDE.md Security Rule 2). `"members can view co-members"` on `org_members` subqueries its own table in its `USING` clause; `"org members can view their org"` on `organizations` subqueries `org_members`, which recurses back into the first policy. The result: **any query against `organizations` under RLS, for any role including `anon`, has always raised `infinite recursion detected in policy for relation "org_members"`** — reproduced directly via `SET LOCAL ROLE anon; SELECT id FROM organizations`. This silently broke the already-shipped `"organizations: anon read active"` policy for every genuine anon caller since it was written; it was never noticed because `/join/[slug]/page.tsx` uses `createServiceClient()`, which bypasses RLS entirely. It was caught here only because this feature's two new anon policies both join through `organizations`, which is the first code path to ever exercise this under RLS with a real `anon` role. Confirmed safe to remove: `org_members` is queried nowhere in live application code (its only reference in `src/` is a static, non-executed SQL snippet on an onboarding error page), and the capability the legacy `organizations` policy provided is already correctly covered by `"organizations: members read own"` (`current_user_org_id() = id`).

## Decisions

**D1 — Route structure: org-scoped under `/join/[slug]`.** `/join/[slug]/courses` and `/join/[slug]/courses/[courseId]`, extending the existing, already-proven org-by-slug lookup rather than introducing a second slug-lookup surface or a global cross-org catalog. This also means no code change to `middleware.ts` is required — its existing `!pathname.startsWith('/join')` passthrough already covers every sub-path. Confirmed by reading `middleware.ts` line 60 directly.

**D2 — Preview depth: full curriculum outline.** The course detail page shows title, description, and the curriculum outline (module and block *titles* only) — never `content`. This mirrors the already-safe narrow column-select the authenticated course detail page uses today (`src/app/courses/[id]/page.tsx`, `course_blocks` select never includes `content`), extended with an additional column-level database grant restriction (see D4) since the anon role's default privileges are broader than the authenticated role's.

**D3 — Opt-in per course, admin/manager only.** `courses.is_public_preview` defaults to `false` for every course, existing and new. Only an org `admin` or `manager` can toggle it (via a new `assertOrgAdminOrPlatformAdmin`-gated Server Action, mirroring the pattern already shipped in COUNCIL-2026-026's `org-settings.ts`) — not a `teacher`, even one who owns the course being toggled. Enabling requires the course to already be `status = 'published'`; a DB-level `CHECK` constraint enforces this atomically regardless of what the application does, closing any window where the flag and status could briefly disagree under concurrent writes.

**D4 — Both RLS and column-level grants must be tightened, not RLS alone.** Two new `TO anon` RLS policies (on `courses` and `course_blocks`) scope rows to `is_public_preview = true AND status = 'published'` joined to `organizations.status = 'active'` — never using `current_user_org_id()`, which is null for an unauthenticated caller, exactly like the existing `organizations` anon policy. In addition, the migration explicitly `REVOKE`s and re-`GRANT`s column-level `SELECT` on `courses` and `course_blocks` to `anon`, naming only the columns safe for public exposure. This is required because of the blanket table-level grant described in Context above — without it, RLS alone would still leave `content` reachable by a direct PostgREST call with the anon key.

**D5 — Non-existence and non-previewability are indistinguishable.** A request for a course that doesn't exist, belongs to an inactive org, isn't marked previewable, or isn't published all return the identical 404 — never a redirect to login, never a different response shape. This prevents a visitor from probing which private courses exist by observing a distinguishing signal.

## Prompt A — Migration: is_public_preview column, RLS, and column-level grants

**Files:**
- `supabase/migrations/20260920200000_public_course_preview.sql` (NEW)
- `supabase/migrations/20260920201500_fix_organizations_org_members_recursion.sql` (NEW — Prompt A.1, added mid-implementation; see Context)

**Scope:** Add the opt-in flag, its atomicity constraint, the two new anon RLS policies, and the column-level grant tightening described in D4.

**Prompt A.1 (corequisite fix, discovered during Prompt A implementation):** Drop the two legacy self-referential RLS policies on `organizations` and `org_members` described in Context — `DROP POLICY "org members can view their org" ON public.organizations;` and `DROP POLICY "members can view co-members" ON public.org_members;`. Without this, Prompt A's own new policies (both of which join through `organizations`) recurse and fail for every real caller, including `anon` — this is not optional cleanup, it is required for this feature to function at all for a real unauthenticated visitor. Verified: dropping both resolves the recursion (`SET LOCAL ROLE anon; SELECT id FROM organizations` succeeds afterward), removes no functionality (superseded by `"organizations: members read own"`), and does not affect any live code path (`org_members` is queried nowhere in `src/`).

**Work:**
1. `ALTER TABLE public.courses ADD COLUMN IF NOT EXISTS is_public_preview boolean NOT NULL DEFAULT false;`
2. `ALTER TABLE public.courses ADD CONSTRAINT courses_preview_requires_published CHECK (is_public_preview = false OR status = 'published');`
3. `CREATE INDEX IF NOT EXISTS idx_courses_public_preview ON public.courses (org_id, is_public_preview, status) WHERE is_public_preview = true AND status = 'published';`
4. `CREATE POLICY "courses: anon public preview" ON public.courses FOR SELECT TO anon USING (is_public_preview = true AND status = 'published' AND EXISTS (SELECT 1 FROM public.organizations o WHERE o.id = courses.org_id AND o.status = 'active'));`
5. `CREATE POLICY "course_blocks: anon public preview" ON public.course_blocks FOR SELECT TO anon USING (EXISTS (SELECT 1 FROM public.courses c JOIN public.organizations o ON o.id = c.org_id WHERE c.id = course_blocks.course_id AND c.is_public_preview = true AND c.status = 'published' AND o.status = 'active'));`
6. `REVOKE SELECT ON public.course_blocks FROM anon; GRANT SELECT (id, title, block_type_id, parent_block_id, sort_order, course_id, org_id, is_published) ON public.course_blocks TO anon;`
7. `REVOKE SELECT ON public.courses FROM anon; GRANT SELECT (id, title, description, status, org_id, is_public_preview) ON public.courses TO anon;`
8. Comment in the migration file explicitly warning that a future `GRANT SELECT ON ALL TABLES IN SCHEMA public TO anon` (as `20260914154000` already did once) would silently re-widen this — flag any such migration in review.

**Security:** This is the load-bearing prompt for the whole feature. Verify directly against a real local Postgres instance (not just reading the SQL) that an `anon`-keyed client genuinely cannot `SELECT content` from `course_blocks` even for a row that the new RLS policy allows — a column-privilege error, not an empty result.

**Verification:**
- `npm run typecheck`
- Direct psql/anon-client check: attempt `.select('content')` as `anon` against a previewable course's block and confirm a column-permission error, not a silent empty response.

**Implementation status:** Complete. `SET LOCAL ROLE anon` against real seeded fixtures (rolled back after, no data left behind) confirmed: (1) allowed columns (`id, title, ...`) return successfully for both `courses` and `course_blocks`; (2) `SELECT content FROM course_blocks` and `SELECT owner_id FROM courses` both fail with `ERROR: permission denied for table ...`, not an empty/filtered result. This required Prompt A.1's recursion fix to even run — the same test failed with the recursion error beforehand, confirming A.1 was a genuine blocker, not defensive-only cleanup.

## Prompt B — Backend: public page data-fetching + admin toggle Server Action

**Files:**
- `src/app/join/[slug]/courses/page.tsx` (NEW)
- `src/app/join/[slug]/courses/[courseId]/page.tsx` (NEW)
- `src/app/actions/org-settings.ts` (MODIFIED — add `setCoursePublicPreview`)
- `src/app/courses/[id]/edit/page.tsx` (MODIFIED — add `is_public_preview` to the existing select, pass to the new toggle component)

**Scope:** Server Components for the two public pages (mirroring `/join/[slug]/page.tsx`'s existing org-lookup pattern exactly, via `createServiceClient()`), and the admin-only toggle Server Action.

**Work:**
1. Catalog page: look up org by slug + `status = 'active'` (identical call shape to `/join/[slug]/page.tsx`); `notFound()` if missing. Query `courses` filtered to `org_id`, `is_public_preview = true`, `status = 'published'`, selecting only `id, title, description`. Empty result renders an empty state, not an error.
2. Detail page: same org lookup; query the single course filtered the same way plus `id = courseId`; a missing row (nonexistent, wrong org, not previewable, not published — D5) all produce the identical `notFound()`. Query `course_blocks` selecting only `id, title, block_type_id, parent_block_id, sort_order`, capped at a fixed limit (e.g. 200), ordered by `sort_order`. The select string must never contain `content` or `gamification` — enforce via grep in PR review.
3. `setCoursePublicPreview(courseId, enable)` in `org-settings.ts`: resolve the course's `org_id`/`status` via `createServiceClient()`; call `assertOrgAdminOrPlatformAdmin(orgId)` (throws `Forbidden` for anyone but admin/manager of that org, or a platform admin — per D3, a teacher-owner is not exempted); if enabling and `status !== 'published'`, return an error without writing; otherwise update `is_public_preview`, re-checking `status = 'published'` in the `WHERE` clause when enabling so a concurrent unpublish is caught even before the DB constraint would reject it; `revalidatePath` the edit page.
4. Edit page: add `is_public_preview` to the existing `courseResult` select; render the new toggle only when `profile.role === 'admin' || profile.role === 'manager'` (not `teacher`, per D3).

**Security:** `setCoursePublicPreview` must reject a non-admin/manager caller and a cross-org write attempt (mirroring the org-settings.ts auth pattern already shipped and tested in COUNCIL-2026-026). The public pages must use `createServiceClient()` for reads (server-side only, never exposed to the browser) — the anon RLS policies from Prompt A are the actual security boundary for any *other* client that queries these tables directly, not a substitute for this app-level filtering.

**Verification:**
- `npm run typecheck`
- `npm test`

## Prompt C — Frontend: catalog/detail rendering + admin toggle UI

**Files:**
- `src/components/lms/PublicCourseCard.tsx` (NEW)
- `src/components/courses/PublicPreviewToggle.tsx` (NEW)
- `src/app/join/[slug]/courses/loading.tsx` (NEW)
- `src/app/join/[slug]/courses/[courseId]/loading.tsx` (NEW)

**Scope:** A dedicated public-safe course card (not a reuse of `src/components/lms/CourseCard.tsx` as-is — that component's footer hard-codes a `/courses/${id}` link to the authenticated route, confirmed by reading it directly, which would silently bounce an anon visitor to `/login` if reused unmodified), the curriculum outline rendering, the "Sign up" CTA, and the admin toggle control.

**Work:**
1. `PublicCourseCard`: title, description, a single link to `/join/[slug]/courses/[courseId]` — no authenticated-route links anywhere in the component.
2. Catalog page renders one `PublicCourseCard` per course; org branding (logo, primary color) from `org.settings.branding`, matching `/join/[slug]/page.tsx`'s existing branding treatment.
3. Detail page: hero (title, description, org branding), curriculum outline grouped by module header with block titles only (no icons or badges that could reveal a block's type, e.g. distinguishing a quiz from a page), a "Sign up" CTA linking to `/join/[slug]`. Zero-block courses render a "curriculum coming soon" message, not an error.
4. `PublicPreviewToggle` (Client Component): calls `setCoursePublicPreview` as a Server Action; disabled state with an inline warning when the course isn't published yet; optimistic toggle with rollback on error (matching the pattern already established for `AutoEnrollSection` in COUNCIL-2026-026 — including handling a thrown rejection, not just a returned `{error}`).

**Security:** No direct Supabase calls from `PublicPreviewToggle` — only the Server Action, which enforces `assertOrgAdminOrPlatformAdmin()`.

**Verification:**
- `npm run typecheck`
- `npm run lint`

## Prompt D — Tests

**Files:**
- `src/tests/e2e/public-course-preview.test.ts` (NEW, real Supabase)
- `src/tests/unit/set-course-public-preview.test.ts` (NEW)

**Scope:** Cover every acceptance criterion, with the same regression-test discipline established in COUNCIL-2026-026 — a security boundary must be proven by exercising it from the actual denied caller's context, not just asserted as intended policy.

**Work — e2e (real local Supabase):**
1. Active org + previewable published course → catalog lists it; card data never includes enrollment/submission counts.
2. Inactive org, nonexistent slug, non-previewable course, unpublished course → all produce the identical not-found result (D5) — assert this from the anon-scoped query path, not just the app-level filter.
3. **The core regression test**: using a real `anon`-keyed Supabase client (not service role, not a mock), attempt `.select('content')` against `course_blocks` for a previewable course's block and assert a column-permission error — proving Prompt A's column-level `REVOKE`/`GRANT` actually holds, not just that the RLS row policy passes. Verify this test would fail against the pre-migration schema before considering it done, the same way COUNCIL-2026-026's trigger regression test was proven by dropping and restoring the trigger.
4. Cross-tenant isolation: a previewable course in org B is never returned when querying under org A's slug.
5. The DB `CHECK` constraint: attempt to insert/update a course to `is_public_preview = true` with `status = 'draft'` and assert the constraint violation.
6. Disabling preview causes an immediate subsequent query to return nothing (no caching window).

**Work — unit (`setCoursePublicPreview`):**
7. Student role → `Forbidden`, no DB write attempted.
8. Enabling on a draft/archived course → returns the specific error, no DB write.
9. Cross-org call → `Forbidden`, mirroring the existing cross-org rejection tests from `org-settings-auto-enroll.test.ts`.

**Security:** Test 3 is the load-bearing test for this entire feature — it must exercise the real `anon` role, not the service-role client, since `service_role` bypasses column grants entirely (`BYPASSRLS`) and would not catch a regression here.

**Verification:**
- `npm run test:ci`
- `npm run test:e2e`
