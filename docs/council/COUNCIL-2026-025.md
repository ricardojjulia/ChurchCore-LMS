# COUNCIL-2026-025 — Pilot Feedback & Error-Triage System

**Date:** 2026-09-18
**Status:** Ratified
**Author:** Platform review (context: closing the "external validation" gate — pilot/demo users currently have no way to report a bug or unexpected result in-product, and unhandled UI errors during a pilot session go completely unobserved)

---

## Context

ChurchCore LMS has no in-product feedback channel and no automatic error capture. When a pilot church admin or student hits something confusing or broken during an uncoached demo session, there is no record of it — the only signal is whatever they happen to mention out loud. This makes "the pilot validated the product" an unverifiable claim.

This mirrors a portable playbook already adapted to this repo's actual stack (Next.js 15 App Router, Supabase/Postgres RLS, `platform_admins`/`is_platform_admin()` staff-access model, Upstash rate limiting). Three things are missing:

1. **Manual capture** — no always-available way for a demo user to flag `BUG` / `ERROR` / `UNEXPECTED_RESULT` / `IMPROVEMENT` in context.
2. **Automatic capture** — `src/app/error.tsx` (the root error boundary) currently only renders a message and dev-console-logs; it reports nothing.
3. **A triage workspace** — there is no staff view to review, dedupe, or act on any of this even if it existed.

---

## Decisions

**D1:** Add one new platform-scoped table, `platform_feedback`, isolated from tenant/org data exactly like `platform_admins` / `platform_audit_log`. RLS restricts all reads/writes to `is_platform_admin()`; the only other access path is `service_role`, used exclusively from the new server route — never from a client.

**D2:** Feature-gate everything behind `NEXT_PUBLIC_DEMO_MODE`. Checked client-side (renders nothing) *and independently re-checked server-side* in the submission route from `process.env.NEXT_PUBLIC_DEMO_MODE` — the client state is never trusted for the gate.

**D3:** Identity and the dedupe fingerprint are always server-derived. The route reads the caller's session via `createClient()` (never a client-supplied user field) and computes a normalized SHA-256 fingerprint server-side from `route + category + (errorMessage || note)`. Any `fingerprint` or identity field the client sends is ignored outright, not merely unused.

**D4:** Reuse `src/lib/rate-limit.ts`'s existing `makeLimiter()` factory (Upstash-backed, already gracefully disables in dev without env vars) rather than inventing a second rate-limiting mechanism. New `feedbackLimiter`, 20 requests / 60s, keyed by session ID.

**D5:** `src/app/error.tsx` is Next.js's actual App Router error-boundary mechanism for this segment tree — extend its existing `useEffect` to report, rather than adding a second, competing React class-component error boundary. No new component needed for automatic capture.

**D6:** Staff triage workspace lives at `src/app/platform/feedback/`, gated the same way every other page under `src/app/platform/` already is (`assertPlatformAdmin()` pattern in `src/app/platform/actions.ts`). Add one link to `PlatformNav.tsx`.

### Prompt B — Submission Route & Fingerprint/Validation Helpers

**Files:**
- `src/lib/feedback.ts` (NEW) — validation + normalization + SHA-256 fingerprint helpers
- `src/app/api/feedback/route.ts` (NEW) — the one submission endpoint

**Scope:** One `POST` route handler implementing the full server contract: gate re-check, validation, server-derived identity, server-derived fingerprint, rate limit, upsert-on-conflict.

**Work:**
1. `src/lib/feedback.ts`:
   - `export const FEEDBACK_CATEGORIES = ['BUG', 'ERROR', 'UNEXPECTED_RESULT', 'IMPROVEMENT'] as const`
   - `export type FeedbackCategory = typeof FEEDBACK_CATEGORIES[number]`
   - `normalizeForFingerprint(s: string): string` — trim, lowercase, collapse whitespace
   - `computeFingerprint(route: string, category: string, detail: string): string` — `crypto.createHash('sha256').update(...).digest('hex')` over the three normalized, `|`-joined fields
   - A `validateFeedbackPayload(body: unknown)` function returning either `{ ok: true; data: {...} }` or `{ ok: false; error: string }`. Bounds: `sessionId` must match the UUID regex; `route` ≤ 200 chars; `category` in `FEEDBACK_CATEGORIES`; `errorMessage` ≤ 500 chars; `note` ≤ 1000 chars; `breadcrumbs` an array of ≤ 5 strings each ≤ 200 chars; `appVersion` ≤ 50 chars; `sessionDurationSeconds` an integer 0–2592000 or null. Reject malformed JSON/wrong types outright with a generic `'Invalid request'` — never echo back what was wrong about a field to avoid giving submission-format hints, matching CLAUDE.md's "never return DB errors directly to the client."
2. `src/app/api/feedback/route.ts`:
   ```typescript
   export const runtime = 'nodejs'

   export async function POST(req: NextRequest) {
     if (process.env.NEXT_PUBLIC_DEMO_MODE !== 'true') {
       return Response.json({ error: 'Not found' }, { status: 404 })
     }

     const parsed = validateFeedbackPayload(await req.json().catch(() => null))
     if (!parsed.ok) return Response.json({ error: parsed.error }, { status: 400 })
     const body = parsed.data

     const { limited } = await checkLimit(feedbackLimiter, body.sessionId)
     if (limited) return Response.json({ error: 'Rate limited' }, { status: 429 })

     const supabase = await createClient()
     const { data: { user } } = await supabase.auth.getUser()
     let userEmail: string | null = null
     let userRole:  string | null = null
     if (user) {
       userEmail = user.email ?? null
       const { data: roleRow } = await supabase
         .from('profile_roles').select('role').eq('auth_id', user.id).maybeSingle()
       userRole = roleRow?.role ?? null
     }

     const detail = body.category === 'ERROR' ? (body.errorMessage ?? '') : (body.note ?? '')
     const fingerprint = computeFingerprint(body.route, body.category, detail)

     const service = createServiceClient()
     const { data: existing } = await service
       .from('platform_feedback').select('id, hit_count').eq('fingerprint', fingerprint).maybeSingle()

     if (existing) {
       await service.from('platform_feedback').update({
         hit_count: existing.hit_count + 1,
         breadcrumbs: body.breadcrumbs,
         session_id: body.sessionId,
         user_email: userEmail,
         user_role: userRole,
         app_version: body.appVersion,
         session_duration_seconds: body.sessionDurationSeconds,
         processed: false,
         triage_action: null,
         updated_at: new Date().toISOString(),
       }).eq('id', existing.id)
     } else {
       await service.from('platform_feedback').insert({
         fingerprint,
         session_id: body.sessionId,
         route: body.route,
         category: body.category,
         error_message: body.category === 'ERROR' ? body.errorMessage : null,
         note: body.category === 'ERROR' ? null : (body.note ?? null),
         breadcrumbs: body.breadcrumbs,
         user_email: userEmail,
         user_role: userRole,
         app_version: body.appVersion,
         session_duration_seconds: body.sessionDurationSeconds,
       })
     }

     return Response.json({ ok: true }, { status: 201 })
   }
   ```
   On any unhandled internal error, catch and return a generic `{ error: 'Something went wrong' }` at 500 — never leak the raw Supabase/driver error, per CLAUDE.md's "Do not return DB errors directly to the client."
3. Identity derivation uses `profile_roles` (the RLS hot-path table), never `profiles`, per CLAUDE.md rule 2.

**Note (post-implementation):** for manual `ERROR`-category submissions, `FeedbackButton` (Prompt C) sends `note`, not `errorMessage` — the fingerprint's `detail` therefore resolves empty for all such reports, collapsing them to one row regardless of content. Fix by falling back to `note` when `errorMessage` is null for the `ERROR` category, or by giving the button an explicit "what happened" field labeled to match `error_message` semantics.

**Security:** Gate re-checked server-side independent of any client state (D2). Identity and fingerprint are 100% server-derived — any `identity`/`fingerprint` field in the request body is simply never read (D3). Rate limit is atomic via the existing Upstash-backed limiter, not process memory (D4). All writes go through `createServiceClient()` — never exposed to the browser.

**Verification:** `npm run typecheck`, `npm run lint`, `npm test` (unit tests added in Prompt E).

## Operational Note (not implementation — record for the team)

Per the source playbook: check the triage queue at least daily during an active pilot, weekly floor otherwise. Prioritize by `hit_count`, not recency. `ERROR` rows are the crash/regression signal — treat a new one as higher priority than a known `BUG`. `IMPROVEMENT` rows are roadmap input, not bugs — route them into the next `council-review` cycle rather than fixing ad hoc. Mark `triage_action` honestly — `acknowledged` is a legitimate resting state; don't mark `fixed` to clear the queue. This system itself is a standing requirement, not a one-time build — a feedback queue nobody reads is worse than not having one.
