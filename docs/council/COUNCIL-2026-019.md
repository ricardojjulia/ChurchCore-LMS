# COUNCIL-2026-019: Scheduled OneRoster Delivery And Reconciliation

**Status:** RATIFIED - Pending Implementation
**Date:** 2026-09-14
**Council:** Architecture Council, ChurchCore LMS (6/6 unanimous)
**Related:** COUNCIL-2026-018, ADR-2026-009, ChurchCore Academy ADR 0069
**Tags:** oneroster, scheduled-exchange, signatures, replay-protection, audit

## Context

COUNCIL-2026-018 completed the first shared OneRoster conformance phase: Academy
fixture parity, LMS validation, explicit identity linking, transactional apply,
bulk reconciliation, provenance guards, and browser verification. M3 must move
the exchange from manual ZIP upload to scheduled transport without storing
provider credentials in LMS, weakening tenant isolation, or silently applying
roster changes.

The existing release workflow also calls `ci.yml` as a reusable workflow even
though `ci.yml` does not declare `workflow_call`. GitHub rejects that release
before creating a job, so release orchestration must be repaired before M3 can
be promoted through staging.

## Council Deliberation

### The Architect

Use a signed inbound delivery boundary for the first scheduled transport slice.
Academy already owns package generation, so Academy should schedule delivery and
LMS should reuse its existing validate, stage, preview, link, apply, history, and
reconciliation pipeline. This avoids remote credentials and arbitrary outbound
URLs in LMS.

### The Engineer

Extract the current upload staging logic into a shared server module. Manual
uploads and signed deliveries should differ only in authentication and transport
metadata. Keep automatic transport separate from operator apply so retries stay
idempotent and failures remain repairable.

### The Security Lead

Use Ed25519 signatures. Academy keeps the private key in its deployment secret
store; LMS stores only the public key and key id. Bind the signature to the
connection id, delivery id, timestamp, and package digest. Enforce a five-minute
clock window, a unique delivery id, a package size limit, and exact content type.
Never persist the ZIP, roster PII, signatures, private keys, or raw provider
errors.

### The Product Owner

Admins need a quiet operational view: whether scheduled delivery is enabled,
when the last package arrived, when the next package is expected, and whether a
received package needs review. Scheduled receipt must not imply automatic apply.

### The QA Lead

Test valid signatures, invalid signatures, stale timestamps, replayed delivery
ids, duplicate package hashes, tenant scoping, disabled connections, malformed
ZIPs, redaction, manual review, and standalone mode. CI must run a disposable
local Supabase stack and fail when E2E discovery is empty.

### The Data Engineer

Add an immutable, tenant-scoped transport-attempt ledger with indexed connection
and creation time. Put public verification material and expected cadence on the
connection row. Use database uniqueness for replay and package idempotency. All
new tables require RLS and service-only writes.

## Decision

Implement M3 as signed scheduled delivery from Academy to LMS.

1. Academy signs each OneRoster ZIP using Ed25519 and sends it to a connection-
   specific LMS endpoint on its schedule.
2. LMS stores the Academy public key, key id, and expected delivery cadence. LMS
   never stores the Academy private key or a reusable provider credential.
3. The signature message is versioned and binds connection id, delivery id,
   delivered-at timestamp, and SHA-256 package digest.
4. A verified delivery is validated and staged through the same code path as a
   manual upload. It is never automatically applied.
5. An authenticated tenant admin or manager previews, links identities, and
   applies a received job through the existing approval boundary.
6. Transport attempts and safe reconciliation counts are visible to tenant
   admins and managers. Raw ZIP content, signatures, roster PII, and raw errors
   are not stored.
7. Standalone mode remains the default and performs no network or scheduled
   work.
8. Repair the reusable CI declaration as a release prerequisite. Staging and
   production deployment still require their existing environment gates.

## Amendments Adopted

1. Automatic apply is prohibited in M3.
2. Automatic Supabase Auth user creation remains prohibited.
3. Only Ed25519 is supported in the first signed-transport profile.
4. Deliveries outside a five-minute clock window are rejected.
5. `delivery_id` must be a UUID and is unique per connection.
6. A package digest may produce only one scheduled import job per connection.
7. Invalid signatures are rejected without persisting attacker-controlled data.
8. Transport audit metadata is allowlisted and must contain no filenames,
   sourced ids, names, email addresses, or raw provider errors.
9. Academy sender implementation must ship through a separate Academy branch
   and PR; LMS work cannot commit or push into the Academy repository.
10. The newly provisioned Supabase project is not treated as staging until the
    project assignment is explicitly confirmed.

## Implementation Mandate

- Continue from `.ai-factory/runs/oneroster-student-data-exchange/state.json`.
- Preserve `src/lib/oneroster` as the transport-independent validation boundary.
- Keep route handlers thin and all service-role operations server-only.
- Add schema changes only through forward migrations with RLS tests.
- Derive tenant scope from the connection selected by the signed endpoint and
  derive operator scope from the authenticated session during preview/apply.
- Use database constraints for replay and package-hash idempotency.
- Do not log request bodies, signatures, public-key parsing details, source ids,
  or database errors.
- Keep the existing 10 MB compressed and 50 MB expanded package limits.

## Implementation Prompt

Implement COUNCIL-2026-019 in numbered order:

1. Repair `ci.yml` so `release.yml` can call it with `workflow_call`, without
   weakening existing push or pull-request CI.
2. Add a forward migration for signed-delivery connection fields, an immutable
   `oneroster_transport_attempts` ledger, replay uniqueness, scheduled package
   idempotency, indexes, grants, and tenant-scoped RLS.
3. Extract reusable validate-and-stage logic from the manual upload route.
4. Add Ed25519 signature parsing and verification as a pure server utility with
   focused unit tests.
5. Add a connection-specific machine delivery endpoint that validates headers,
   size, timestamp, signature, connection state, replay, and package digest,
   then stages but does not apply the package.
6. Add authenticated connection configuration, received-job preview, transport
   history APIs, and admin UI states for disabled, active, overdue, failed,
   duplicate, and awaiting-review deliveries.
7. Add route, RLS, migration, idempotency, redaction, and standalone-mode tests.
8. Run fresh migrations, pgTAP, unit, E2E, typecheck, lint, version, build,
   browser, secret-scan, and diff verification before opening the LMS PR.
9. Prepare the Academy sender in a separate clean Academy worktree only after
   explicit repository authorization, then prove cross-repo scheduled delivery.

## Definition Of Done

- [ ] `ci.yml` is valid as both a normal and reusable workflow.
- [ ] Connection configuration stores only public verification material.
- [ ] Valid signed ZIP deliveries create one staged job and one audit attempt.
- [ ] Invalid, stale, disabled, malformed, replayed, and duplicate deliveries
      return safe outcomes with no raw package persistence.
- [ ] Scheduled receipt never applies roster changes automatically.
- [ ] Tenant admins can review transport state and preview received jobs.
- [ ] RLS prevents cross-tenant transport and connection reads or writes.
- [ ] Standalone tenants perform no exchange work.
- [ ] Full local and hosted verification passes before merge.
- [ ] Academy sender and cross-repo runtime proof ship through a separate PR.
