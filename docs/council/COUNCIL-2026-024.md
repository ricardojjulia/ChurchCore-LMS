# COUNCIL-2026-020 — Spanish (es) Localization, Phase 1: Student/Parent-Facing Surface

**Date:** 2026-09-18
**Status:** Ratified
**Author:** Platform review (context: user asked "do we have a Spanish translation?" — answer was no; user then supplied a reusable `language-translation` pipeline and asked to run it)

---

## Context

ChurchCore LMS has no i18n infrastructure at all — no library, no locale files, no language switcher. All UI strings are hardcoded English JSX text.

A full-app scan (Agent 1 of `.claude/skills/language-translation/SKILL.md`, installed this session for reuse on any future language request) found the true scope is much larger than a single pass can respectively cover: **~717 raw hardcoded strings across just the sampled files**, with dozens of routes and ~96 feature components not yet even scanned. Full coverage is realistically 1000+ strings across 130+ files.

Shipping a translation that only covers a fraction of the app — where some screens are Spanish and others silently stay English — reads as broken, not unfinished. The user was asked to choose a scope and picked: **translate the student/parent/guardian/general-member-facing surface first**, deferring admin/platform/HQ internal tooling (assumed English-comfortable staff audience) to a later phase.

---

## Decisions

**D1 — Scope boundary for this phase:** landing, login, student dashboard, courses (student catalog + detail + learning/block-player experience — NOT course builder/edit/analytics/submissions/gradebook), messages, calendar (list + new-event form, not admin-only scope options), announcements, certificates, leaderboard, notifications, guardian portal, student performance reports, profile, my-groups, onboarding, offline page, join flow, and the shared nav shell (Sidebar, MobileBottomNav, NotificationBell, GlobalSearch, SignOutButton, OfflineBanner). Explicitly excluded: everything under `src/app/admin/`, `src/app/platform/`, `src/app/hq/`, `(reports)/admin/`, `(reports)/instructor/`, course-builder/staff-only UI branches embedded in otherwise-shared pages, and `MobileAdminDrawer.tsx`. Staff-only branches inside in-scope files (e.g. the "Academic Placement" / Builder-Analytics-Submissions section of the course detail page) are left in English — a Spanish-speaking student never renders that branch, so this creates no mixed-language experience for the actual target audience.

**D2 — New dependency: `next-intl`, in cookie-based "without i18n routing" mode.** No i18n library exists today. The generic pipeline's own default for an undetected library is `react-i18next`, but this is a Next.js 15 **App Router** project with Server Components — `react-i18next` has no first-class RSC support, `next-intl` does. Flagged here per `CLAUDE.md`'s "Do not add new dependencies without mentioning it" rule.

`next-intl`'s standard setup restructures the entire `src/app/` tree under a `[locale]/` dynamic segment and installs its own routing middleware. This repo already has a load-bearing root `middleware.ts` (Supabase session refresh + auth-gated route redirects) that every page depends on. A full path-based locale restructure would move/rewrite ~130+ route files and risks breaking that auth flow. Instead: use `next-intl` in its documented **cookie-based, no-routing-integration mode** — locale stored in a cookie (e.g. `NEXT_LOCALE`), read via `getRequestConfig`, no `[locale]` URL segment, no new routing middleware, existing `middleware.ts` untouched (it may optionally read the same cookie to pass locale through, but must not have its auth logic altered). The language switcher sets the cookie and triggers a reload/refresh rather than navigating to a localized path.

**D3 — Register:** formal "usted" throughout, neutral/international Spanish (not region-specific), appropriate for a professional church/education product read by administrators, teachers, students, and parents across many Spanish-speaking countries.

**D4 — Terminology, ratified by native-speaker review (Agent 3):**

| Term | Chosen | Rejected | Why |
|---|---|---|---|
| Guardian | Acudiente | tutor, apoderado | Neutral across regions, avoids narrow legal connotation |
| Reports | Informes | Reportes | Avoids anglicism |
| Terms (academic) | Períodos | Términos | Avoids future collision with "términos y condiciones" |
| Blueprints | Plantillas | Planos | Natural for course templates, not architecturally literal |
| Manager (role) | Encargado | Gerente | "Gerente" is corporate/retail jargon, wrong register for ministry staff |
| Teacher | Docente | Profesor(a) | Gender-invariant, fits mixed-audience formal register |
| Dashboard | Panel | Panel de control, Inicio | Matches existing one-word nav-label pattern |
| Build (course builder verb) | Diseñar | Construir | Natural software-authoring verb, not staff-facing anyway per D1 |
| Bug (feedback category) | Defecto | Error | Avoids visual collision with "Error o fallo" in the same dropdown |

**D5 — Pluralization:** Spanish plural/agreement doesn't map to English's `(s)` suffix pattern. Every count-bearing string got a real ternary construction with correct noun/verb/adjective agreement (e.g. `{n} {n === 1 ? 'curso está marcado' : 'cursos están marcados'} en riesgo`), not a literal `(s)`/`(es)` suffix.

**D6 — Brand/product names stay untranslated:** "ChurchCore LMS", "Project HQ"/"HQ", "OneRoster", "Zoom", "Google Meet", "Microsoft Teams", "YouTube Live".

## Implementation Prompt (Agent 4 — Code Generator)

**Files:** new `src/i18n/` config + `messages/en.json` + `messages/es.json`, `next.config.ts` (or wherever Next config lives), `src/middleware.ts` (new or edited), every file listed in the state file's `text_map`/`translations_approved` entries (~50 files across the D1 scope), plus a new or extended language switcher component.

**Scope:** Wire up `next-intl` from scratch (no existing i18n to follow), replace every hardcoded string in `text_map` with the corresponding `translations_approved` key/value, and add a language switcher.

**Work:**
1. `npm install next-intl` (new dependency — see D2).
2. Read the state file at the scratchpad path (`translation-es.json` — ask the orchestrator for the exact path if not already known) — use `translations_approved`, `text_map`, and `qa_summary.terminology_decisions`.
3. Set up `next-intl` in its **cookie-based, no-routing-integration mode** (see D2) — READ `middleware.ts` at the repo root first, in full, before writing anything: it is the existing Supabase auth session-refresh + route-protection middleware and must keep working exactly as it does today. Do NOT create a `[locale]/` route segment, do NOT move or rename any existing route file, and do NOT replace or chain a second routing middleware in front of it. Concretely: a `src/i18n/request.ts` (or equivalent) that reads the locale from a cookie (e.g. `NEXT_LOCALE`, defaulting to `'en'`) via `next/headers`' `cookies()`, and a `NextIntlClientProvider` mounted in `src/app/layout.tsx` (alongside the existing `FeedbackSessionProvider`/`Toaster`/etc. — additive, not a restructure) wrapping `{children}` with messages loaded via `getMessages()`/`getRequestConfig`. If `next-intl`'s current documented API for this mode differs in specifics, follow its actual current docs for "without i18n routing" rather than guessing — the constraint that matters is: no `[locale]` path segment, no new routing middleware, `middleware.ts`'s existing auth logic byte-for-byte unchanged (it may read the same locale cookie to forward it, nothing more).
4. Create `messages/en.json` (English source values — the original `text_map.text` values, keyed the same way) and `messages/es.json` (from `translations_approved`, keyed by each entry's `key`). Respect the D1 scope — do not invent keys for admin/platform/HQ content that wasn't translated.
5. For every file in `text_map`, replace the hardcoded string with `useTranslations()`/`getTranslations()` + the matching key from `translations_approved`. Preserve every interpolation placeholder and pluralization construction from D5 exactly — do not simplify back to a `(s)` suffix.
6. Add a language switcher (EN/ES) in a sensible always-visible location (near the existing Sidebar/nav shell) following this repo's existing component conventions — check `src/components/layout/` for the nearest analogous pattern (e.g. how `NotificationBell` or `SignOutButton` are structured and mounted) rather than inventing a new pattern.
7. Do not touch any file outside the D1 scope — leave admin/platform/HQ hardcoded English exactly as-is for the later phase.

**Security:** No security-sensitive surface here (no new data access, no RLS, no new endpoint) — but confirm the locale-routing middleware change doesn't interfere with the existing auth middleware/session handling, if this repo has one, by reading it first.

**Verification:** `npm run typecheck`, `npm run lint`, `npm run build` (locale routing changes are exactly the kind of thing that looks fine in dev and breaks the production build), manual: switch to Spanish and confirm the in-scope pages render Spanish while admin/platform/HQ pages remain English (expected, not a bug).

**Accepted deviation, not a defect:** `SidebarClient.tsx`'s admin/platform-only nav item labels (Users, Cohorts, Billing, HQ, Platform Admin, etc.) were translated along with the rest of that shared component, even though the *destinations* those links point to remain English (Phase 2). This is intentional for internal consistency of one shared nav component — a student never renders those destinations, and a bilingual admin isn't harmed by seeing "Facturación" in their own sidebar pointing to an English billing page.

**Incident, no deliverable impact:** during Agent 5's QA run, a shell-quoting bug destroyed the pipeline's own scratchpad handoff file (`translation-es.json` in the session's `/private/tmp` scratchpad — not part of the repo, not source code). All git-tracked source changes and `messages/en.json`/`messages/es.json` were unaffected. Flagged here for the record and as a note for hardening `.claude/skills/language-translation/SKILL.md`'s Agent 3→4 data handoff (the `key`/`category` fields were also dropped from `translations_approved` at one point and had to be reconstructed by matching against `translations_draft` — worth making that contract more robust before the next language run).

**Phase 2 (explicit follow-up, not started):** `src/app/admin/`, `src/app/platform/`, `src/app/hq/`, `(reports)/admin/`, `(reports)/instructor/`, `MobileAdminDrawer.tsx`, and all course-builder/staff-only UI remain English-only.
