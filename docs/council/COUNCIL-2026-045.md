# COUNCIL-2026-045: Password Sign-In That Works, and Abuse Protection

**Status:** RATIFIED — in implementation
**Date:** 2026-09-28
**Council:** Architecture Council, ChurchCore LMS (6/6 approve, 2026-09-28; owner directed the work the same day: "make sure that people can signup and login with their creds, have scaffolding to suppress abuse, or bots, or hacking attempts")
**Related:** COUNCIL-2026-034 (self-serve signup), COUNCIL-2026-037 (SSO — **tabled** by the owner on 2026-09-28; the code stays, off by default), `src/app/(auth)/login`, `src/app/join`, `src/lib/turnstile.ts`, `src/lib/rate-limit.ts`
**Tags:** auth, security, abuse, bots

## Context

A review of email-and-password sign-in on 2026-09-28 found these problems:

1. **New members can't sign in (production defect).** In production, email confirmation is required (`mailer_autoconfirm = false`). `/join` creates the user with `email_confirm: false` and sends no confirmation email, so the automatic sign-in after joining fails with "Email not confirmed". The member lands on `/login`, and signing in there fails the same way. Locally, confirmations are off, which is why the suite never caught it.
2. **There is no password reset.** Nothing calls `resetPasswordForEmail` or `updateUser({ password })`. A forgotten password is a dead end.
3. **Church admins from `/start` have no password.** `/api/signup/verify` creates the admin without one and signs them in with a one-time link. When that session ends, they can't sign in again.
4. **Supabase Auth public sign-up is on** (`disable_signup = false`). Anyone with the public anon key can create accounts directly against `/auth/v1/signup`, skipping the Turnstile check on `/join` and `/start`. Every legitimate account is created server-side with the admin API, so public sign-up isn't needed while SSO is tabled.
5. **Login has no abuse protection.** It calls `signInWithPassword` from the browser. The app applies no rate limit and no bot check, and it shows raw auth error text.
6. **The app's rate limits are optional.** They are no-ops unless Upstash is configured, and the local suite can't exercise them at all.
7. **The password policy is weak.** Supabase's minimum is 6 characters, `/join` checks length only in the browser, and there is no common-password check.

## Decision

1. **Postgres-backed auth throttle.** A private `auth_throttle` table plus an atomic `auth_throttle_hit(key, max, window)` function, callable by the service role only. Keys are SHA-256 hashes (`ip:`, `email:`, `org:` prefixes), so no raw email or IP is stored. Auth limits no longer depend on Upstash, and the local suite tests them for real.
2. **Server-side login.** `POST /api/auth/login` does, in order:
   - Per-IP limit (30 per 10 minutes).
   - Turnstile check.
   - Per-email limit (10 attempts per 15 minutes, cleared on success).
   - `signInWithPassword` with the cookie-bound server client.
   Every credential failure, including "email not confirmed", returns the same generic message. If the deployment has no Turnstile keys, sign-in and reset skip the bot check (the limits still apply) rather than locking everyone out; `/join` and `/start` always require it. The login page adds a Turnstile widget and a "Forgot password?" link.
3. **Password reset.**
   - `/forgot-password` posts to `POST /api/auth/forgot`, which applies a per-IP limit, Turnstile and a per-email limit.
   - The response is always the same, whether or not the account exists.
   - For an existing account, the server generates a recovery link with the admin API and sends it with Resend using the app's own template, not Supabase's mailer.
   - The link opens `GET /auth/reset`, which verifies the token into a session and redirects to `/account/password`.
   - If email isn't configured for the site, the endpoint says so (503). This is site-wide, not per account.
   - Verifying a recovery link also confirms the email, so members stuck by defect 1 can recover this way.
4. **Set or change a password** at `/account/password` (server action `updatePassword`). A current password is required unless the session came from a recovery or one-time link in the last 30 minutes. That covers reset links and admins from `/start` who have no password yet. After a change, the user's other sessions are signed out. The page is linked from the profile page, and `/start` admins are sent there straight from their verification link (replacing the old `/onboarding` placeholder as the landing page).
5. **Harden `/join`.**
   - Per-IP limit (10 per hour) and per-org limit (60 per hour).
   - Turnstile receives the client IP.
   - Server-side password policy.
   - Accounts are created confirmed (`email_confirm: true`), which fixes defect 1. Email ownership isn't proven at join; the address owner can always take the account back through password reset.
6. **Password policy** (`src/lib/password-policy.ts`), enforced on the server wherever the app sets a password:
   - 8 to 72 characters.
   - Not the email address or its local part.
   - Not on a built-in list of the most common passwords.
   Supabase's own minimum goes up to 8.
7. **Turn off Supabase public sign-up** (`enable_signup = false` locally; `disable_signup = true` in production). Re-enabling SSO later means revisiting this, because first-time OAuth users need it on. That is recorded in COUNCIL-2026-037.
8. **Security events.** `auth_security_events` records throttle hits, failed Turnstile checks and password resets. It stores hashed identifiers only, can be written only by the service role, and can be read only by platform admins. The platform overview page (`/platform`) shows the last 24 hours by event type.

## Amendments Adopted

1. **No enumeration.** Login failures, the forgot-password response and the limits behave the same whether or not an email is registered. Only site-wide conditions (email not configured, the IP limit) may differ.
2. **No PII at rest in the new tables.** Only SHA-256 hashes of IPs and emails are stored, never the raw value. Nothing new is written to the logs with an email address.
3. **Sessions.** A password change signs out the user's other sessions. The recovery-session exemption from entering the current password lasts 30 minutes.
4. **Tests.** Each new surface has `covers()` tests, pgTAP covers the throttle function and both tables' RLS, and the suite seed clears `auth_throttle` so repeated local runs don't lock themselves out.

## Test Surfaces

`api:POST /api/auth/login`, `api:POST /api/auth/forgot`, `api:GET /auth/reset`, `page:/forgot-password`, `page:/account/password`, `action:account.updatePassword`.

## Definition of Done

- A member who joins through `/join` is signed in and can sign in again later.
- Reset works end to end, and the old password stops working.
- An admin from `/start` goes straight from the verification link to choosing a password (`/account/password?welcome=1`) and can then sign in with it.
- The limits and Turnstile are enforced on the server, and no endpoint leaks whether an account exists.
- Public sign-up is off locally and, once the owner approves it, in production.
- `npm run verify`, `supabase test db` and the full local suite pass. The CHANGELOG has an entry and `version:check` passes.

## Rollout (owner-approved production changes)

After the release: set Supabase Auth `disable_signup = true` and `password_min_length = 8`. Password reset emails need `RESEND_API_KEY` in Vercel; until then, `/forgot-password` says reset email isn't available. The auth limits work without Upstash.
