# COUNCIL-2026-032 — Security Hotfix: Profile Privilege Escalation (retroactive record)

**Date:** 2026-09-24
**Status:** Ratified (retroactive — emergency security fix)
**Author:** Platform review, at the direction of the project owner (Ricardo Julia)
**Found by:** the COUNCIL-2026-031 test-suite build (admin user-management flow)

## Context

While building the full test suite, the admin flow showed that changing a user's role had no effect. Tracing it found the opposite problem as well: the `profiles` UPDATE policy (`uid = current_user_uid()`) plus a table-wide UPDATE grant let **any signed-in user set their own `role` and `org_id`** through PostgREST. `trg_sync_profile_roles` copies both into `profile_roles`, which every RLS helper trusts, so a single request made a user an admin of any tenant. This was reproduced locally with the public anon key. Production has the same policy. A second path existed: `handle_new_user()` took role and org from sign-up `user_metadata`.

## Decision

Ship immediately as a hotfix (PR #29, release 0.34.3) rather than through a full council cycle, because the exposure is live and trivially exploitable. This follows the same practice as the #27 `/api/ai` open-proxy fix. The fix follows existing project rules; no new architecture is introduced:

- **D1:** column-level UPDATE grant on `profiles` limited to personal fields. Authorization data changes only through the service role or `SECURITY DEFINER` functions.
- **D2:** role and tenant come only from server-controlled `app_metadata`, both at user creation and on change (sync trigger). All trusted creation paths set it.
- **D3:** admin user-management actions write through the service role and are scoped to the admin's own org, with no self-targeting.

## Verification

- Unit `src/app/actions/admin.test.ts` (7 tests).
- Real-database E2E subset: 66/66.

- Read-only production review: admin counts per org look plausible. The owner will confirm Biblos's two admins.

## Follow-up

COUNCIL-2026-031's suite covers these paths going forward: the admin flow exercises role and status changes, and the surface gate requires every new action to ship with a test.
