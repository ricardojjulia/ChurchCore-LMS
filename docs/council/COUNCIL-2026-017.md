# COUNCIL-2026-017 - OneRoster Student Data Exchange

**Date:** 2026-09-05
**Status:** Proposed
**Author:** Council review (context: ChurchCore Academy to ChurchCore LMS student data exchange)

---

## Context

ChurchCore LMS needs a standards-based way to exchange student, course, class, and enrollment data with ChurchCore Academy while preserving LMS standalone operation. The candidate standard is OneRoster 1.2 from 1EdTech.

Current product boundary:

1. **ChurchCore Academy** is the SIS and official academic records system.
2. **ChurchCore LMS** is the learning delivery system: content, blocks, progress, submissions, certificates, analytics, and student learning experience.
3. **ChurchCore LMS must remain standalone** for churches and schools that do not use Academy.

Current LMS evidence and constraints:

- Next.js is currently `^16.2.9` in `package.json`; some docs still reference older Next versions.
- Supabase and RLS are the security boundary. Service-role access is allowed only in narrow server-only paths.
- Live schema drift must be resolved before OneRoster implementation: `courses.status` has replaced older `courses.is_published`, `course_sections.is_active` exists where some code/tests expect `status`, and cohort naming is inconsistent across docs/code/live database assumptions.
- `supabase db lint --linked` connects to the cloud project but reports existing function issues that should be fixed before adding new integration tables and sync paths.

Official standard references:

- 1EdTech OneRoster overview: https://www.1edtech.org/standards/oneroster
- OneRoster 1.2 standard: https://standards.1edtech.org/oneroster/specifications/standards/v1p2
- OneRoster conformance testing: https://www.1edtech.org/standards/oneroster/conformance-testing

---

## Council Positions

**Architect:** Adopt OneRoster as an optional interoperability layer, not as a replacement for the native LMS data model. Use LMS-native UUIDs as primary keys and keep OneRoster `sourcedId` values in mapping/provenance tables.

**Engineer:** Implement CSV package import first. CSV gives deterministic validation, preview, quarantine, idempotent apply, and admin approval before production data changes. REST and scheduled sync should follow only after CSV semantics are stable.

**Security Lead:** Treat roster, enrollment, guardian, grade, and progress data as student education records and PII. Use field allowlists, tenant-scoped credentials, no browser-visible tokens, no raw student PII in logs/audit/AI prompts, and soft-deactivation instead of destructive deletes.

**Data Engineer:** Normalize imports into staging tables before touching core LMS tables. Every imported object needs a source mapping row keyed by `(org_id, source_system, object_type, sourced_id)`.

**Product Owner:** Standalone LMS remains first-class. Academy-connected mode is an organization-level setting. Local creation and manual CSV import continue for standalone organizations.

**QA Lead:** Do not begin implementation until schema drift, DB lint blockers, stale tests, and the `next lint` script problem are addressed or explicitly isolated. RLS and cross-tenant tests are P0.

---

## Decisions

**D1:** ChurchCore LMS will support OneRoster 1.2 as an optional org-level integration. Default mode is `standalone`; no Academy or OneRoster configuration is required to run the LMS.

**D2:** First implementation target is OneRoster 1.2 CSV Consumer in LMS. Supported initial files are `manifest.csv`, `orgs.csv`, `users.csv`, `roles.csv`, `academicSessions.csv`, `courses.csv`, `classes.csv`, and `enrollments.csv`.

**D3:** `demographics.csv`, guardian/agent data, gradebook/result exchange, resource exchange, and REST APIs are explicitly deferred. Each requires a separate council review or an amendment to this record.

**D4:** Academy-managed records must carry provenance and be protected from accidental local overwrite. The UI may allow local read/inspect and explicitly approved detach/reconcile flows, but normal edit forms must not silently mutate Academy-managed fields.

**D5:** Imports must be staged, validated, previewed, and approved before applying. Direct import into `profiles`, `profile_roles`, `academic_terms`, `course_blueprints`, `course_sections`, or `direct_enrollments` is prohibited.

**D6:** Sync deletions become soft-deactivations or withdrawals. Imported data must not hard-delete profiles, learning progress, submissions, grades, certificates, or audit history.

**D7:** Academy and LMS do not share databases or Supabase service-role keys. Academy-to-LMS exchange uses OneRoster packages or future tenant-scoped API credentials only.

## Target Data Mapping

| OneRoster Entity | LMS Target | Notes |
| --- | --- | --- |
| `orgs` | `organizations` or tenant-scoped external org references | Do not allow import package to set server-derived `org_id`. |
| `users` | `profiles` | Create or link learner/staff profile records; do not use `sourcedId` as primary key. |
| `roles` | `profile_roles` | Preserve existing role/permission model; map unsupported roles to quarantine. |
| `academicSessions` | `academic_terms` | Preserve LMS term behavior and access window semantics. |
| `courses` | `course_blueprints` | Academy catalog course maps best to LMS blueprint. |
| `classes` | `course_sections` | OneRoster class maps to scheduled LMS section. |
| `enrollments` | `direct_enrollments` | Let the existing LMS enrollment bridge populate delivery `enrollments`. |
| `agents` / guardians | deferred | Opt-in only; requires separate privacy review. |
| `results` | deferred | Return final evidence only, not raw learning activity, after explicit approval. |

## Application Plan

### Phase 0 - Preflight Stabilization

**Goal:** Remove known drift before adding a student-data integration.

Work:

1. Fix stale `courses.is_published` usage in `src/lib/dashboard/context.ts`.
2. Fix stale enrollment bridge test names: `student_uid` and `enrollment_status`.
3. Fix live DB lint issues:
   - `get_block_discussion_replies`: ambiguous `user_id`
   - `get_guardian_students`: missing `profiles.xp`
   - `get_guardian_student_overview`: missing `profiles.xp`
   - `record_engagement_event`: boolean/integer operator error
   - `resolve_term_config`: JSONB assignment warning
4. Replace or repair the stale `npm run lint` script that still calls removed Next.js lint behavior.
5. Reconfirm local and linked Supabase schema shape before writing OneRoster migrations.

Verification:

- `npm run typecheck`
- `npm run version:check`
- `npm run test:run`
- `supabase db lint --linked`
- targeted `rg -n "is_published|student_uid|enrollment_status|from\\('cohorts'\\)" src tests supabase`

### Phase 1 - OneRoster CSV Parser And Validator

**Goal:** Validate packages without mutating production records.

Work:

1. Add `src/lib/oneroster/` with schema definitions, CSV parsing, ZIP validation, role mapping, field allowlists, and normalized entity types.
2. Validate `manifest.csv` and required CSV headers.
3. Enforce package size, file count, row count, and decompressed-size limits.
4. Reject unexpected executable content, nested archive tricks, path traversal names, malformed CSV, duplicate `sourcedId`, unsupported roles, missing references, and cross-tenant mappings.
5. Produce a dry-run diff: create/update/unchanged/deactivate/quarantine counts.

Security:

- Parse server-side only.
- Never trust `org_id` from the package.
- Do not emit raw row payloads in API errors or logs.

### Phase 2 - Admin Import UI

**Goal:** Give org admins/managers a safe import workflow.

Likely files:

- `src/app/admin/integrations/oneroster/page.tsx`
- `src/app/admin/integrations/oneroster/import/page.tsx`
- `src/app/api/integrations/oneroster/import/route.ts`
- `src/app/api/integrations/oneroster/jobs/[id]/route.ts`

Workflow:

1. Upload package.
2. Validate and stage.
3. Show preview counts and quarantined row reasons.
4. Require explicit confirmation before apply.
5. Apply idempotently.
6. Show job history and last sync status.

UI rules:

- Standalone orgs see OneRoster as optional.
- Academy-managed orgs see provenance labels and read-only indicators on managed records.
- No student PII should appear in toast errors, console logs, or audit metadata.

### Phase 3 - Idempotent Apply Engine

**Goal:** Safely map valid staged records into LMS tables.

Work:

1. Create/update profiles from OneRoster `users` using field allowlists.
2. Map OneRoster roles into LMS `student`, `teacher`, `admin`, and `manager`; unsupported roles quarantine.
3. Create/update academic terms, course blueprints, sections, and direct enrollments.
4. Use `external_entity_links` for every imported object.
5. Use soft deactivation for inactive/deleted records.
6. Record audit events with counts and hashes only.

Server boundary:

- Authenticated org admin/manager starts and approves imports.
- Service role may apply mutations only after deriving `org_id` from the authenticated session or connection record.
- Every mutation must include the derived `org_id`.

### Phase 4 - Academy CSV Provider

**Goal:** Let ChurchCore Academy export tenant-scoped OneRoster packages that LMS can import through the same path.

Academy mapping:

- `academy_institution_profiles` / `academy_institution_subdivisions` -> `orgs`
- `academy_academic_years` / `academy_academic_periods` -> `academicSessions`
- `academy_people` plus student/staff role assignments -> `users` and `roles`
- `academy_courses` -> `courses`
- `academy_course_sections` -> `classes`
- `academy_course_section_registrations` -> `enrollments`

Academy implementation should reuse existing provider-neutral `lms-contract` and `lms-roster-source` patterns where possible.

### Phase 5 - Scheduled Academy Pull

**Goal:** Automate tenant sync after manual package import is proven.

Work:

1. Add tenant-scoped connection credentials.
2. Pull signed Academy exports on a scheduled job.
3. Stage and validate exactly like manual CSV import.
4. Auto-apply only when tenant policy allows and destructive deltas are below configured thresholds.
5. Alert admins when quarantine or destructive-delta thresholds are exceeded.

### Phase 6 - REST And Result Return

**Goal:** Add live OneRoster REST only after CSV import/export is stable.

Deferred scope:

- OAuth/token lifecycle
- token rotation and revocation
- API rate limits and retry policy
- request signing/replay protection where applicable
- conformance testing
- grade/result return

Default result-return rule:

- Disabled by default.
- Return reviewed completion/final-grade evidence only.
- Do not return raw quiz answers, discussion content, tutor logs, AI prompts, or behavior analytics.

## Standalone Mode Contract

ChurchCore LMS remains usable without Academy or OneRoster:

1. No required Academy environment variables.
2. No required Academy network calls during app boot, login, dashboard, course learning, admin user management, or enrollment flows.
3. Existing manual user invite/import remains available.
4. Existing course, section, cohort, and enrollment administration remains available.
5. New OneRoster tables may exist in the database, but empty/inactive connection records must not change behavior.
6. Organization mode defaults to `standalone`.
7. Tests must prove a tenant with no OneRoster connection can create users/enrollments and complete learning workflows.

---

## Security And Privacy Requirements

Non-negotiables:

1. RLS on every new table.
2. No student PII in logs, raw API errors, analytics metadata, audit metadata, or AI prompts.
3. No OneRoster credentials in client code, browser storage, audit records, or organization settings JSON.
4. Tenant-scoped credentials only; no cross-system Supabase service-role sharing.
5. Field allowlists for every imported file.
6. Guardian/agent data is opt-in and deferred from the initial implementation.
7. Raw package retention is disabled by default. If retained, store only in private storage with short retention and strict org-scoped access.
8. Sync deletes are soft deactivations.
9. Cross-tenant `sourcedId` collision and package-org mismatch are hard failures.
10. All import job records and mapping rows are immutable enough to support audit and incident review.

---

## Acceptance Criteria

1. LMS standalone mode works with no Academy/OneRoster configuration.
2. Org admin can upload a OneRoster 1.2 CSV ZIP and receive validation results without applying changes.
3. Preview clearly reports create/update/unchanged/deactivate/quarantine counts.
4. Import apply is idempotent by `(org_id, source_system, object_type, sourced_id)`.
5. Cross-tenant mappings are blocked by tests.
6. Unsupported roles and malformed rows are quarantined, not silently coerced.
7. Academy-managed records show provenance and are protected from accidental local overwrite.
8. No raw student PII appears in audit metadata, server logs, client errors, or analytics events.
9. RLS tests cover same-org allowed, cross-org blocked, unauthenticated blocked, and suspended tenant blocked.
10. Existing LMS local user/course/enrollment workflows still pass.
11. `npm run typecheck`, project test suite, relevant E2E/RLS tests, and Supabase lint pass or have documented unrelated blockers.
12. A follow-up ADR is written before REST sync, credential exchange, guardian data, or result return.

---

## Material Risks

1. Existing schema drift can make OneRoster mappings unsafe unless fixed first.
2. Service-role import code can bypass RLS if `org_id` is not derived and enforced server-side.
3. OneRoster packages may contain more student data than LMS needs.
4. Same email across tenants can collide with current invite/account assumptions.
5. Partial package application can corrupt rosters without staging and quarantine.
6. REST sync introduces credential lifecycle, replay, rate-limit, and operational risks.
7. Guardian/agent and result return data materially increase privacy obligations and should not enter the first phase.

#### Academic Apply Verification Follow-Up (2026-09-07)

Continue the current academic-only increment; identity linking remains deferred.
Apply staged academic rows through one service-only, security-invoker Postgres
function. Verify the actor's active tenant and staff role inside the transaction,
lock the job and source scope, and commit each academic mutation together with

redacted quarantine reason. A job-level failure rolls back the transaction.

`validating` until staging succeeds, and require matching staged row counts at
apply. Test replay, cross-tenant access, suspended tenants, failed mutations,
and imports larger than the REST row limit. This implements the existing
idempotency and tenant-isolation requirements without expanding identity scope.
