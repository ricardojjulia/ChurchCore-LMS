# COUNCIL-2026-031 — Full Application Test Suite & "Features Ship With Tests" Gate

**Date:** 2026-09-23
**Status:** Ratified
**Author:** Platform review, at the direction of the project owner (Ricardo Julia). Owner decisions taken in-session on 2026-09-23: (1) production gets a **full synthetic-user** post-release suite, not read-only smoke; (2) the coverage rule is a **hard CI failure**, not a warning.

---

## Context

On 2026-09-23 the release pipeline turned green for the first time since PR #21 (ADR-2026-011). The same day's Copilot backlog review found real defects that had shipped unnoticed for weeks — a tenant-isolation gap in the anon `course_blocks` policy, a course-existence oracle in a Server Action, a quiz timer that burned time before questions loaded. None was caught by tests, because the tests that exist cover only a slice of the product.

**Inventory (2026-09-23, `origin/main` @ `a737f6f`):**

| Surface | Count | Current automated coverage |
|---|---|---|
| Pages (`src/app/**/page.tsx`) | 85 | **0 browser tests.** No Playwright/Cypress in the repo. |
| API Route Handlers (`src/app/api/**/route.ts`) | 28 | ~8 exercised by `src/tests/e2e` (health, feedback, search, oneroster via unit mocks) |
| Server Actions (exported from `src/app/actions/*.ts`) | 82 | A handful via unit tests with mocked Supabase; Server Actions cannot be called from Vitest e2e (they need Next request context) |
| Edge Functions (`supabase/functions/*`) | 10 | `search-users`, `system-health-check` only |
| pgTAP (`supabase/tests`) | 17 files | Solid for RLS helpers; runs in CI |

Existing infrastructure worth keeping: `.github/workflows/e2e.yml` already boots a **disposable local Supabase stack**, applies every migration, runs pgTAP, seeds two orgs + six users (`scripts/ci-setup-test-env.mjs`, `supabase/seed.test.sql`), serves Edge Functions, and starts the app. The seed has **no `manager`** and **no dedicated platform admin** (CI borrows `teacher@` and inserts a `platform_admins` row mid-test).

There is also no mechanism that forces a new feature to arrive with tests. Council docs *describe* test plans (COUNCIL-2026-029/030 did), but nothing verifies the plan was delivered, and nothing notices when a new page or route has zero coverage.

## Decisions

**D1 — Playwright is the single harness for browser *and* HTTP API tests.** Add dev dependencies `@playwright/test` (^1.63) and `@axe-core/playwright` (^4.13). Both are dev-only: no bundle or edge-runtime impact. Playwright's `request` fixture shares cookie `storageState` with the browser, so one role-login setup serves both API and UI specs. Vitest stays for unit tests and the existing DB-level e2e specs (`npm run test:e2e`); nothing is migrated away from it.

**D2 — Layout.**
```
tests/playwright/
  playwright.config.ts          — projects: setup, api, browser (chromium desktop), mobile (Pixel 7 viewport), prod-synthetic
  fixtures/roles.ts             — role registry: admin, manager, teacher, student, guardian, platform, admin-b, student-b, anon
  fixtures/auth.setup.ts        — signs each role in once, writes .auth/<role>.json storageState
  fixtures/data.ts              — deterministic seed IDs (courses, blocks, paths, orgs) shared by specs
  fixtures/covers.ts            — covers(...surfaceIds): no-op at runtime, the coverage checker's anchor
  api/*.spec.ts                 — one spec per API area
  browser/pages.spec.ts         — generated sweep: every page × every role
  browser/flows/*.spec.ts       — deep user journeys per feature
  prod/*.spec.ts                — prod-synthetic subset (D8)
tests/surface/
  exemptions.json               — time-boxed exemptions (D6)
scripts/test-surface.mjs        — discovers surfaces + checks coverage (D5)
```

**D3 — Roles are first-class.** Every spec states which roles it runs as. The seed adds `manager@test.churchcore.dev` (Org A, role `manager`) and `platform@test.churchcore.dev` (Org A member, inserted into `platform_admins` by the seed, replacing the mid-test insert pattern for new specs). The existing six users keep their emails and UUID namespaces.

**D4 — Three test tiers, each with a defined bar.**
1. **Page sweep (every page).** For each of the 85 pages, a route table declares the roles allowed and the fixture params for dynamic segments. For each allowed role: HTTP < 400, no Next error overlay / error boundary text, no uncaught page errors or `console.error`, a `<main>` landmark, and **zero `serious`/`critical` axe violations** (known violations may be listed as time-boxed exemptions, D6). For each *disallowed* role: redirected to login/dashboard or shown the forbidden state — never the page content. Anonymous: every protected page redirects to `/login`.
2. **API contract (every route).** For each of the 28 routes and each exported method: unauthenticated → 401 (or the route's documented public behaviour); wrong role → 403; malformed body → 400 with no DB error text leaked; unknown id → 404; cross-org id → 404/403 (never another tenant's data); happy path where the route has no paid third-party dependency. Routes that call Stripe/OpenAI/Anthropic/Resend get auth/validation/not-configured coverage in CI; their happy path is covered with the provider unset → graceful 503/500 with a generic message.
3. **Feature flows (every feature).** Journeys that drive real UI and therefore exercise Server Actions end-to-end: course authoring (create → blocks → publish → public preview toggle), enrollment (self, auto-enroll, bulk), learning (lesson/quiz/assignment submit, quiz timer + bank draw), grading (submissions page + gradebook grid, teacher-ownership rule), learning paths (admin CRUD, student progress), guardian portal, messaging, announcements, calendar, certificates + verify page, leaderboard, notifications, groups (capacity), org settings/branding/join links, OneRoster (upload → validate → preview → apply, signed delivery via API), platform console (tenants, feedback triage), reports. Each flow cleans up what it creates (or uses per-run unique names inside the disposable CI stack).

**D5 — The coverage manifest is derived, not hand-maintained.** `scripts/test-surface.mjs` discovers surfaces from the filesystem:
- `page:<route>` from every `page.tsx` (route groups stripped, e.g. `page:/courses/[id]/gradebook`)
- `api:<METHOD> <route>` from every exported `GET|POST|PUT|PATCH|DELETE` in `route.ts`
- `action:<file>.<name>` from every `export async function` in `src/app/actions/*.ts`
- `edge:<name>` from every `supabase/functions/*` directory (excluding `_shared`)

It then scans `tests/**`, `src/tests/**`, `src/**/*.test.ts(x)` and `supabase/tests/**` for `covers('…')` string literals (and, for SQL, `-- covers: …` comments). **Every discovered surface must be covered or exempt.** Output: a human-readable report and `--json`. `npm run test:surface` runs it; it needs no services, so it runs in the fast `ci.yml` workflow.

**D6 — Exemptions are explicit and expire.** `tests/surface/exemptions.json` entries: `{ "surface", "reason", "owner", "expires" (YYYY-MM-DD) }`. The checker fails on an expired exemption, on an exemption for a surface that no longer exists, and on an exemption for a surface that is now covered (stale). Maximum exemption lifetime: 60 days. Legitimate standing exemptions (e.g. an Edge Function that only runs on a cron against paid services) must still be re-dated deliberately.

**D7 — CI shape.**
- `ci.yml` gains a **Test Surface** job (`npm run test:surface`) — required status check.
- `e2e.yml` gains a **Browser & API** job: same disposable stack, but the app runs as a **production build** (`next build && next start`) so tests see what ships; installs Chromium only; runs projects `api`, `browser`, `mobile`; uploads the HTML report + traces on failure.
- The existing Vitest e2e job is unchanged.
- Add both new checks to the branch-protection list in `docs/github-setup.md`.

**D8 — Production synthetic suite (owner decision: full synthetic user).** A dedicated synthetic tenant runs a `@prod` subset after every release.
- **Tenant:** org slug `synthetic-qa`, name "ChurchCore Synthetic QA", new column `organizations.is_synthetic boolean NOT NULL DEFAULT false` (migration), set `true`. Platform metrics/tenant lists and Stripe flows exclude `is_synthetic` orgs; the org is never on a paid plan.
- **Accounts:** one per role (admin, manager, teacher, student, guardian) at the reserved domain **`@synthetic.churchcore.invalid`** (RFC 2606 — undeliverable by construction). No platform-admin synthetic account (platform powers are cross-tenant; not worth the blast radius).
- **Email safety:** `sendEmail()` and `send-guardian-notifications` drop any recipient ending in `.invalid` before calling Resend (and unit tests prove it). This protects sender reputation even if a synthetic flow triggers a notification.
- **Bootstrap:** `scripts/prod-synthetic-bootstrap.mjs`, run **once, locally, by the owner**, with the production service-role key from their own shell (never stored in GitHub). Idempotent. Creates the org, the auth users with a generated password, profiles, and a baseline course. Prints the password once for the owner to store as a GitHub secret.
- **Secrets (production environment):** `SYNTHETIC_BASE_URL`, `SYNTHETIC_PASSWORD`. Emails are derivable (`<role>@synthetic.churchcore.invalid`) and live in code.
- **What it does:** logs in as each synthetic role, loads that role's core pages, and runs reversible write flows confined to the synthetic org (create → verify → delete a course, enroll/unenroll, post/delete an announcement, submit a quiz, grade in the gradebook grid, create/delete a learning path). Every created record carries a `[synthetic <run-id>]` prefix; an `afterAll` sweep deletes that run's records; a separate idempotent cleanup step deletes any `[synthetic ` records older than 24h (catches crashed runs). **No AI endpoints, no Stripe, no OneRoster apply** in production.
- **Release integration:** `release.yml` gains a `Production synthetic checks` job after `deploy` (needs: deploy, environment: production for the secrets). Failure marks the release red and fires `DEPLOY_WEBHOOK_URL` if set. It does not roll back automatically.

**D9 — Governance: features ship with tests, mechanically.**
- CLAUDE.md "Testing Standards" gains: every new page/route/action/edge function must be `covers()`-tagged by at least one test in the same PR; `npm run test:surface` is part of `npm run verify`.
- Council template requirement: every future council doc includes a **"Test surfaces"** section listing the surface IDs it adds and the spec files that will cover them. `implementation-validator` (Gate 3) and `pr-review` check it.
- `.github/pull_request_template.md` gains a checklist: surfaces added, specs added, `test:surface` green, prod-synthetic impact.
- `docs/testing.md` (new) documents how to run each tier locally, how to add a role, how to write a flow, how exemptions work.

**D10 — Explicitly out of scope.** Visual regression/screenshot diffing; load/performance testing; cross-browser beyond Chromium + a mobile viewport; mutation testing. Each is a separate decision if needed later.

Create `tests/playwright/playwright.config.ts` per D2 (baseURL from `APP_BASE_URL`, default `http://127.0.0.1:3000`; `retries: 1` in CI; trace `retain-on-failure`; reporter `list` + `html`). Add `.auth/`, `playwright-report/`, `test-results/` to `.gitignore`.

### Prompt B — Surface checker
Implement `scripts/test-surface.mjs` per D5/D6 with a Vitest unit test covering discovery (route groups, dynamic segments, multiple methods per route file, `_shared` exclusion), tag scanning, and every exemption failure mode. Add `test:surface` to `verify`.

### Prompt C — API contract suite
One spec per area (`health`, `auth`, `ai`, `analytics`, `calendar`, `certificates`, `digest`, `feedback`, `guardian`, `oneroster`, `reports`, `search`, `stripe`, `upload`), each `covers()`-tagging the exact `api:<METHOD> <route>` IDs. Apply the D4.2 bar. Stripe webhook: unsigned and badly signed payloads rejected; no payload echoed. Upload: org-scoped path enforced, non-image rejected.

### Prompt D — Page sweep
A route table (`browser/routes.ts`) listing all 85 pages with allowed roles and dynamic params (from `fixtures/data.ts`). `pages.spec.ts` generates tests from it per D4.1 for projects `browser` and `mobile`. The table is itself checked: the checker fails if a `page:` surface has no table row.

### Prompt E — Feature flows
Implement the D4.3 journeys, tagging every Server Action they exercise with `covers('action:<file>.<name>')` and the pages they drive. New features from COUNCIL-2026-027/029/030 and today's fixes (quiz timer, public preview, OneRoster duplicate handling) get dedicated flows. Remaining actions not reachable through UI get targeted API/DB-level coverage or a dated exemption with a reason.

### Prompt F — CI + governance
Wire D7 into `ci.yml`/`e2e.yml`, update `docs/github-setup.md` branch-protection list, update CLAUDE.md Testing Standards, add the PR template and `docs/testing.md` (D9), update the council template section in `docs/CODE-FACTORY-SYSTEM-PROMPT.md`.

### Prompt G — Production synthetic
Migration for `organizations.is_synthetic` (+ RLS unaffected: column only; platform queries filter it). Email `.invalid` guard in app + edge function with unit tests. `scripts/prod-synthetic-bootstrap.mjs`. `tests/playwright/prod/*.spec.ts` + `prod-synthetic` project (`baseURL` = `SYNTHETIC_BASE_URL`). `release.yml` job per D8. Document the owner's one-time setup in `docs/testing.md`.

## Acceptance

1. `npm run test:surface` passes on `main` with every surface covered or exempt; exemptions ≤ 60 days, each with a reason.
2. The `Browser & API` job runs the full suite against a production build on every PR, green.
3. A PR that adds a page without a covering test fails the `Test Surface` check (proven by a checker unit test fixture).
4. After the owner completes the one-time bootstrap, the next release runs the synthetic suite against production and leaves no `[synthetic ` records older than the run.
5. No email is sent to any `.invalid` address (unit-proven).

## Findings from the first full run (2026-09-24)

Building the suite and running it against a clean database surfaced defects that
existing tests missed. These are fixed in this change, each with a test:

| Area | Defect | Fix |
|---|---|---|
| Messaging | RLS recursion between `message_threads` and `thread_members` meant no thread could be created or read (production has 0 threads). Non-members could post into a thread by id. | `current_user_thread_ids()` helper; posting requires membership; `org_id` stamped on new threads; ambiguous `profiles` embed fixed |
| Learner progress | `course_progress` was never written. Assignment, quiz, video and discussion submissions failed (`org_id`/`enrollment_id` missing). Bank-only quizzes could not be played. | `sync_my_course_progress()`; BEFORE INSERT trigger stamps `block_submissions`; BlockPlayer renders bank quizzes |
| Tenancy on insert | Many inserts omitted `org_id` (announcements, calendar events, and others) and failed RLS. | `DEFAULT current_user_org_id()` on 57 tables |
| Attendance | Self check-in and teacher marking both failed. `markStudentAttendance` was not org-scoped. | uid-based writes; org scoping |
| Feature gaps | Drafts could not be published. Badges had no write policies. Cohort members never listed. Students could not create personal events. `/join/[slug]` crashed (sync params). `/verify` was blocked for anonymous visitors. | Publish button; badge RLS; `auth_id` join; personal-event policy; async params; public route |
| Data loss | Content autosave could overwrite newer edits. | Lost-update guard + test |
| Guardians | Guardian emails never sent (wrong settings column); unsubscribe broken. | `notification_prefs.guardian_emails` |
| Storage | `content-images` and `reports` buckets were missing in production. | Migration creates both (private) |
| Access control | `/hq` and course analytics pages were not gated. The `/callback` `next` parameter was an open redirect. | Staff gates; `safe-redirect` |
| Edge Functions | Cron functions failed open when `CRON_SECRET` was unset. `generate-embedding` and `generate-certificate` accepted the anon key. The release only deployed two functions. | `rejectUnlessCron` / `rejectUnlessServiceRole`; release deploys every function |
| Error hygiene | Raw database errors were returned to clients in 11 places. | Generic messages (+ i18n keys) |
| Platform | CSP blocked Supabase realtime. Many WCAG contrast and labelling failures. | CSP origin; a11y fixes (remaining ones dated in `a11y-known.json`) |

Known defects, recorded with `test.fail()` so the suite flags when they are fixed.
**All closed by COUNCIL-2026-033 (0.36.0).**

- **PDF generation** (certificate PDF, report PDF exports) crashes: `@react-pdf/renderer` runs on
  the project's React 18 inside Next 16's bundled React 19. It needs a React 19 upgrade.
- **Large reports** invoke Edge Functions that do not exist (`generate-student-report`,
  `generate-gradebook-report`).
- **Weekly digest**: `weekly-digest` calls `/api/ai/weekly-summary` with cron auth, which the
  route rejects, so digests never send.
- `/guardian/[studentId]` shows staff an empty page. The page allows staff, but the RPC denies them.
- Duplicate `id="main-content"`; unlabelled inputs on some admin forms (`a11y-known.json`,
  expires 2026-11-20).
- Performance: each page makes about 28 `getUser` calls, driven by link prefetch.
- Gamification integrity: `record_engagement_event` is executable by any signed-in user with a
  caller-chosen `p_xp`, so XP and leaderboards can be inflated directly through PostgREST. The
  unused `recordEngagement` Server Action wrapper is removed here; the RPC needs server-side XP
  values per event type.
