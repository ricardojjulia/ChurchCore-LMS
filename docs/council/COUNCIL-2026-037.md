# COUNCIL-2026-037: SSO and Social Login (Google, Microsoft, ChurchCore)

**Status:** RATIFIED — Google and Microsoft shipped in 0.40.0 but **tabled by the owner on 2026-09-28**: providers stay off (`NEXT_PUBLIC_SSO_PROVIDERS` unset). Before turning them on, re-enable Supabase Auth sign-up, which COUNCIL-2026-045 turned off, because first-time OAuth users need it. ChurchCore sign-in follows COUNCIL-2026-038.
**Date:** 2026-09-26
**Council:** Architecture Council, ChurchCore LMS (6/6 approve, 2026-09-27; owner approved the Q4 plan 2026-09-26)
**Related:** COUNCIL-2026-032 (role and org only from `app_metadata`), COUNCIL-2026-038 and ADR-2026-012 (ChurchCore sign-in), `/callback` (`safe-redirect`)
**Tags:** auth, sso, oauth, oidc, identity, security

## Context

Users sign in with email and password only. Schools and larger churches expect "Sign in with Google" or "Sign in with Microsoft". Churches running ChurchCore want members to use one account across the ChMS and the LMS. Supabase Auth supports Google and Azure (Microsoft) OAuth, and custom OIDC providers.

## Decision

1. **Google and Microsoft sign-in**, for everyone, through Supabase OAuth. They appear on `/login` and on the `/join/[slug]` registration page.
2. **"Sign in with ChurchCore"** through OIDC, for orgs with an active ChurchCore Connect connection (COUNCIL-2026-038). ChurchCore acts as the OIDC provider (built in the ChurchCore repo).
3. **Org-level enforcement (optional):** an org can require SSO for its staff, allow-list email domains, and turn off passwords for its members.
4. **Account linking.** A user who signs in with a provider whose verified email matches an existing account is asked to confirm with their password or an emailed link before the identities are linked. There's no silent linking by email.

## Amendments Adopted

1. **Signing in never grants org membership or a role.** A new OAuth user without an invite, a `/join` registration, or a ChurchCore Connect identity link lands with no org and an explanation. Role and org still come only from `app_metadata`, set by trusted server paths (COUNCIL-2026-032).
2. The OAuth `redirect_to` and `next` values go through the existing `safeNextPath`. No new open-redirect surface.
3. ChurchCore sign-in maps to an LMS profile only through `external_entity_links` (`source_system='churchcore'`), never by email alone.
4. Provider client secrets live in Supabase Auth configuration and Vercel environment variables only. `.env.local.example` documents their names.
5. **Account linking (replaces Decision 4's confirmation step).** Supabase Auth links a provider identity to an existing account automatically when the provider reports the email as verified, and a custom confirmation step can't be inserted into that flow. The binding rule is therefore: only providers that verify email are enabled. Google always does; Microsoft must be configured with the `email` and `xms_edov` optional claims, so unverified Microsoft emails create a separate account instead of linking.
7. **Known, accepted behaviour (PR review).** (a) The SSO join step lets any signed-in account without an organization join an active org through its public join link. This is the same bar as the password join page, which anyone with the link can use to create an account; a member removed from an org can rejoin through a join link unless the org stops sharing it. (b) `/auth/sign-out` is a GET, because a Server Component redirect can only issue a GET. A third-party page can therefore end a user's session, but it can't read or change anything; the `reason` value is allow-listed.
6. **Enforcement:** the org policy (require SSO for staff, allowed email domains, passwords off) is checked server-side on every page load in the root layout using the verified JWT `amr` claim; a violating session is signed out with an explanation. The admin action refuses any policy that would reject the saving admin's own session.
