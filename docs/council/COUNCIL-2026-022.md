# COUNCIL-2026-022: Enforce Group Capacity at the Database Boundary

**Status:** IMPLEMENTED AND VERIFIED LOCALLY — Architect review pending

**Related:** COUNCIL-2026-020, COUNCIL-2026-021; PR #5

## Context and deliberation

An authenticated local admin inserted a second membership into a group with
`max_members = 1`. The UI disables adding members at capacity, but the database
and server action allow overfilling. This confirms the earlier PR review concern.

- **The Architect:** Enforce the existing group invariant in Postgres, without a new service or identity model. Vote: Yes.
- **The Engineer:** Lock the destination group before checking count so parallel requests serialize. Preserve duplicate membership handling and unlimited groups. Vote: Yes.
- **The Security Lead:** Use invoker privileges and existing RLS. Deny inaccessible parents; expose only a fixed capacity error through the action. No service-role bypass. Vote: Yes.
- **The Product Owner:** Honor the maximum that staff already configure. Never remove existing members automatically. Vote: Yes.
- **The QA Lead:** Prove rejection, available capacity, unlimited groups, movement, limit updates, and a two-session race. Rerun tenant/platform regressions and E2E. Vote: Yes.
- **The Data Engineer:** Use a forward, idempotent migration. Existing over-capacity groups keep their members; future additions are rejected. Locking must also serialize with group limit updates. Vote: Yes.

## Decision and amendments

1. Add an invoker trigger on membership INSERT or group movement. Lock the
   destination group row, verify it is visible within the membership tenant,
   then compare its maximum with existing membership count.
2. Reject reductions below current count when the maximum is changed. Preserve
   existing over-capacity data and allow removals, role edits and unchanged limits.
3. Use a stable SQL error code with a fixed safe action message. Retain existing
   role, tenant, section, provenance and platform read-only boundaries.
4. No historical migration rewrite, cloud write, new dependency, Academy work,
   production approval or human-review override. This is an existing-feature
   repair, not a new major LMS roadmap.
