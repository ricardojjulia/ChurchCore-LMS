# COUNCIL-2026-018: Shared OneRoster Exchange Standard

**Status:** RATIFIED - Phase 2 Conformance Implemented
**Date:** 2026-09-12
**Council:** Architecture Council, ChurchCore LMS (6/6 unanimous)
**Related:** ADR-2026-009, COUNCIL-2026-017, ChurchCore Academy ADR 0069
**Tags:** oneroster, academy, lms, interoperability, rostering, gradebook

## Context

ChurchCore Academy and ChurchCore LMS need one shared alignment standard. Academy owns SIS facts. LMS owns course delivery. Existing Academy `lms-contract` interfaces and the LMS OneRoster importer overlap, but the shared standard needs to be ratified explicitly and executed as a cross-repository program.

OneRoster is the closest fit for roster, class, enrollment, academic-session, and gradebook exchange. Ed-Fi remains the broader SIS/data-hub reference, PESC remains the official transcript/registrar exchange lane, and CLR remains the learner-owned credential lane.

## Decision

The council ratifies OneRoster as the shared communication standard between ChurchCore Academy and ChurchCore LMS.

The LMS implementation will evolve from admin-upload importer into a standards-complete receiving and result-return service for Academy:

- OneRoster CSV package import remains the first transport.
- OneRoster Rostering Service endpoints are the target API transport.
- OneRoster Gradebook Service style payloads are the target result-return contract.
- All imported records carry provenance, source status, source hash, audit evidence, and reconciliation behavior.

## Amendments Adopted

1. LMS standalone mode must remain fully functional without Academy or OneRoster configuration.
2. Source data cannot create or escalate LMS administrator, manager, guardian, parent, aide, proctor, or relative roles without explicit approval.
3. Automatic Auth user provisioning remains out of scope until a later identity council decision.
4. User PII may be validated as roster data but must be redacted from staged payloads, logs, and AI prompts.
5. Grade and progress return to Academy must be reviewed import data, not official records.
6. Cross-repo fixtures must prove Academy exports can be consumed by LMS.
7. Linked database verification is required for apply, preview, provenance guards, identity linking, and bulk omission reconciliation.

## Implementation Mandate

Preserve the existing LMS implementation under `src/lib/oneroster`, `src/app/api/integrations/oneroster`, `src/app/admin/integrations/oneroster`, and `supabase/migrations/20260907*` to `20260908*`.

Continue from `.ai-factory/runs/oneroster-student-data-exchange/state.json`, which records `identity_linking_verified`.

Do not bypass RLS. Do not import service clients into client components. Do not log roster PII. Do not auto-create Auth users. Do not expose raw provider payloads.

## Implementation Prompt

Use the software factory to continue the shared OneRoster exchange implementation across ChurchCore Academy and ChurchCore LMS. In Academy, start from ADR 0069 and the `src/modules/oneroster-contract` export module. In LMS, start from ADR-2026-009, this council decision, and the existing OneRoster importer. Build the next phase: repository-backed Academy export from real tenant data, an authenticated Academy export preview/download route, a shared conformance fixture, and an LMS test that validates and previews that fixture without manual edits. Preserve LMS standalone mode and keep identity provisioning deferred.

## Definition of Done

- [x] Academy exports OneRoster packages from persisted tenant academic data.
- [x] LMS imports Academy-generated packages with no manual changes.
- [x] Cross-repo fixtures pass in both repositories.
- [x] Identity linking remains explicit and tenant-scoped.
- [x] No secrets or passwords are exported or persisted.
- [x] RLS and service-only apply boundaries remain verified.
- [x] Browser verification covers preview, apply, history, and managed-field UI.
- [x] Tests, typecheck, lint, build, linked db lint, pgTAP suites, concurrency harness, and diff checks pass.
