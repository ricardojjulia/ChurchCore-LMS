# COUNCIL-2026-035: Teacher ↔ Guardian Messaging

**Status:** RATIFIED — in implementation (Sprint 6)
**Date:** 2026-09-26
**Council:** Architecture Council, ChurchCore LMS (6/6 approve, 2026-09-26; owner approved the Q4 plan the same day)
**Related:** Council Review 3 competitive gap #5 (the last open item), migration `20260923200000_fix_messaging_rls_recursion.sql`, `guardian_links`, ADR-2026-010
**Tags:** communication, guardians, messaging, rls

## Context

Messaging works (fixed in 0.35.0), but it only connects org members to one another. A guardian can see a ward's progress, grades and certificates, yet can't message the ward's teacher, and a teacher can't reach a struggling student's parent. K-12 tools treat this as standard. It is the last open item on Council Review 3's gap list.

## Decision

1. **Allowed pairs**, and only these:
   - a guardian ↔ any teacher of a course their linked ward is actively enrolled in;
   - a guardian ↔ the org's admins and managers.

   Guardians can't message students, other guardians, or teachers unrelated to their ward.
2. **Entry points:**
   - "Message teacher" on `/guardian/[studentId]` next to each course;
   - "Message guardian" in the teacher's gradebook grid and on the submission review, shown only when the student has a linked guardian.
3. **Threads are about one student.** `message_threads.subject_student_uid` records which student the conversation concerns. It's shown in the thread header and used for access checks.
4. **Link lifecycle.** When a guardian link is removed or the enrollment is dropped (a completed course still counts), the thread becomes read-only for the guardian and new messages are blocked. History is kept.
5. **Notifications:** new messages notify through the existing notification center and guardian email queue (ADR-2026-010 retry and dead-letter), with the existing unsubscribe preference.

## Amendments Adopted


1. Pair eligibility is enforced in the database with a `SECURITY DEFINER` helper, `can_message_about(student_uid, other_uid)`, used by the messages INSERT policy, not only in the UI. No `SET row_security = off`.
2. Staff can't use a guardian thread to message the student. The student isn't a participant unless an admin adds them explicitly.
3. Minors: a student under 13 never receives direct messages from a guardian-facing thread.
4. The guardian email notification carries no message body, only "You have a new message about {student first name}" and a link. The body stays in the app.
5. **Close the thread self-join hole (found during investigation).** The `message_threads` and `message_thread_participants` INSERT policies were OR'd with org-only checks, so any org member could add themselves to any thread (given its id) and read it, and could create a thread naming someone else as its creator. All thread and participant rows are written by server actions with the service role, so the user-level INSERT policies are dropped entirely.
6. `searchUsers` interpolated raw input into a PostgREST `or()` filter. Input is now escaped so it can't change the filter.
