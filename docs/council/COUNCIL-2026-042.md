# COUNCIL-2026-042: SCORM and xAPI Runtime

**Status:** DRAFT — pending council vote and owner approval
**Date:** 2026-09-26
**Council:** Architecture Council, ChurchCore LMS (vote pending)
**Related:** ADR-2026-013 (supersedes ADR-2026-006), the `scorm` block type (in the schema, with no builder or player)
**Tags:** scorm, xapi, interoperability, content, security

## Context

Christian schools and denominations buy SCORM content: safeguarding, child-protection, volunteer screening, compliance. Without SCORM the product fails those evaluations. The `scorm` block type already exists in `block_types` with no builder form or player. ADR-2026-013 brings SCORM into the roadmap.

## Decision

1. **Upload** a SCORM 1.2 or SCORM 2004 (3rd/4th edition) zip in the builder. It's validated (`imsmanifest.xml`, launch file, size limit) and unpacked to the private storage bucket under `{org_id}/scorm/{package_id}/`.
2. **Runtime.** The package's launch page is served in a sandboxed iframe from a separate origin (see Amendments). A first-party runtime shim implements the SCORM 1.2 `API` and 2004 `API_1484_11` objects. Commits go to our API, which maps `cmi.core.lesson_status` / `cmi.completion_status`, `cmi.success_status`, score and session time onto block completion and score. Suspend data is kept for resume.
3. **xAPI:** an LRS endpoint (`/api/xapi/statements`) accepts statements from xAPI (cmi5-style) packages launched with an auth token scoped to the learner and block. Completion and score statements map the same way.
4. SCORM and xAPI results appear in the gradebook grid, progress and certificates like any other block.

## Amendments Adopted

Proposed; binding once voted.

1. **Isolation.** Package content is untrusted HTML and JavaScript. It's served from a separate content domain (or a Vercel rewrite to a dedicated host) with `Content-Security-Policy: sandbox allow-scripts allow-forms` and no access to the app's cookies. The runtime shim talks to the app through `postMessage` with origin checks. Package JavaScript must never run on the app origin.
2. Files are fetched through short-lived signed URLs (storage rule: `{org_id}/…` paths). They're never public.
3. **Uploads are scanned:** zip-bomb limits, path-traversal rejection (`../`), an allow-list of file types, and a maximum unpacked size.
4. The xAPI endpoint accepts statements only for the token's learner and block. Actor spoofing is rejected.

## Test Surfaces

- `api:POST /api/scorm/packages` (upload and validate), `api:POST /api/scorm/[blockId]/commit`, `api:POST /api/xapi/statements`: `tests/playwright/api/scorm.spec.ts` (authentication, cross-org denial, bad manifest, traversal zip, zip bomb, actor spoofing, completion mapping).
- The builder SCORM form and player: `flows/scorm.spec.ts` with a minimal SCORM 1.2 and 2004 fixture (commit → completion → gradebook).
- Unit: data-model mapping for 1.2 and 2004.

## Definition of Done

- [ ] 1.2 and 2004 fixtures complete and score correctly; suspend and resume works; xAPI completion works
- [ ] Separate-origin sandbox verified: package JavaScript can't read app cookies or call app APIs directly
- [ ] Tests green; CHANGELOG and status report updated
