# COUNCIL-2026-029 — Learning Paths / Discipleship Tracks

**Date:** 2026-09-22
**Status:** Ratified
**Author:** Autonomous cloud loop (daily/2026-09-22-learning-paths)

---

## Context

Every course in ChurchCore LMS exists as a standalone unit. Churches naturally run structured programs — "New Member Track," "Leadership Development Series," "6-Week Marriage Course" — that group multiple courses into an ordered sequence with a defined start and end. An unordered list of courses cannot model this; learners have no sense of where they are in a larger program.

Every consumer LMS ChurchCore competes with (Teachable, Thinkific, Kajabi) treats "learning paths" or "course bundles with progression" as table-stakes features. This gap was implicitly ranked by the Council Review 3 feature agent (Agent 4, `docs/reviews/2026-09-19-council-review-3-agent-4-features.md`) as the next natural step after auto-enrollment (COUNCIL-2026-026, shipped) and public catalog (COUNCIL-2026-027, shipped).

The feature is additive and opt-in: existing courses are unchanged; organizations that don't use paths see nothing different. A path surfaces as a new section in the admin management UI and as a new view in the learner dashboard.

## Decisions

**D1 — Org-scoped opt-in.** `learning_paths.org_id` isolates paths per tenant. RLS mirrors `courses` exactly: members read their org's published paths; admins and managers read and write all of their org's paths; platform admins read all.

**D2 — Ordered course membership.** `learning_path_courses(path_id, course_id, sort_order)` with a unique constraint on `(path_id, course_id)`. `sort_order` is a small integer; the admin UI presents up/down reorder controls (no drag-and-drop required in v1) and the backend re-numbers `sort_order` on reorder.

**D3 — Only published courses may be added to a path.** Enforced in the Server Action; a DB-level `CHECK` constraint is not practical here (course status can change after insertion), but the action verifies `status = 'published'` at add-time and the learner query filters to published courses anyway.

**D4 — Path publication is independent.** `learning_paths.is_published` gates learner visibility. An admin can draft a path while assembling its courses, then publish when ready. Unpublishing a path hides it from learners but does not affect the underlying courses.

**D5 — No hard prerequisites in v1.** Learners can begin any course in a path in any order. The path surface shows aggregate progress (N of M courses complete) without blocking. Prerequisites as a hard gate are deferred.

**D6 — Path progress is derived, not stored.** A learner's path progress is computed at query time from `course_certificates` (one row per completed course). No new enrollment or progress table is needed.

## Prompt A — Migration: learning_paths and learning_path_courses tables

**Files:**
- `supabase/migrations/20260922120000_learning_paths.sql` (NEW)

**Scope:** Create both tables, enable RLS, add all policies, and add indexes.

**Work:**
1. Create `public.learning_paths`:
   - `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
   - `org_id uuid NOT NULL REFERENCES public.organizations(id) ON DELETE CASCADE`
   - `title text NOT NULL CHECK (char_length(title) BETWEEN 1 AND 200)`
   - `description text`
   - `is_published boolean NOT NULL DEFAULT false`
   - `cover_image_url text`
   - `created_at timestamptz NOT NULL DEFAULT now()`
   - `updated_at timestamptz NOT NULL DEFAULT now()`
2. `ALTER TABLE public.learning_paths ENABLE ROW LEVEL SECURITY;`
3. Create `public.learning_path_courses`:
   - `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
   - `path_id uuid NOT NULL REFERENCES public.learning_paths(id) ON DELETE CASCADE`
   - `course_id uuid NOT NULL REFERENCES public.courses(id) ON DELETE CASCADE`
   - `sort_order integer NOT NULL DEFAULT 0`
   - `created_at timestamptz NOT NULL DEFAULT now()`
   - `UNIQUE (path_id, course_id)`
4. `ALTER TABLE public.learning_path_courses ENABLE ROW LEVEL SECURITY;`
5. Indexes:
   - `CREATE INDEX idx_learning_paths_org_published ON public.learning_paths (org_id, is_published);`
   - `CREATE INDEX idx_learning_path_courses_path_order ON public.learning_path_courses (path_id, sort_order);`
   - `CREATE INDEX idx_learning_path_courses_course ON public.learning_path_courses (course_id);`
6. `updated_at` trigger on `learning_paths` (reuse the existing `handle_updated_at` trigger function already defined in migrations).
7. RLS policies on `learning_paths`:
   - Members (authenticated): `SELECT` where `is_platform_admin() OR current_user_org_id() = org_id AND is_published = true`
   - Admins/managers: `SELECT` (all, not filtered by is_published) `WHERE is_platform_admin() OR (current_user_org_id() = org_id AND current_user_role() IN ('admin','manager'))`
   - Admins/managers: `INSERT` — `WITH CHECK (current_user_org_id() = org_id AND current_user_role() IN ('admin','manager'))`
   - Admins/managers: `UPDATE` — `USING (current_user_org_id() = org_id AND current_user_role() IN ('admin','manager'))`
   - Admins/managers: `DELETE` — `USING (current_user_org_id() = org_id AND current_user_role() IN ('admin','manager'))`
   - Platform admins: full read (covered by `is_platform_admin()` in the SELECT policies above)
8. RLS policies on `learning_path_courses` — scope through `learning_paths` to inherit the same org isolation:
   - `SELECT`: `EXISTS (SELECT 1 FROM public.learning_paths lp WHERE lp.id = path_id AND (is_platform_admin() OR current_user_org_id() = lp.org_id))`
   - `INSERT/UPDATE/DELETE`: same EXISTS but also `current_user_role() IN ('admin','manager')`

**Note on policy split:** Use separate policies for member read vs. admin read to avoid ambiguity, following the pattern used in `courses` RLS policies.

## Prompt B — Backend: Server Actions for path CRUD and learner data-fetching

**Files:**
- `src/app/actions/learning-paths.ts` (NEW)
- `src/types/learning-path.ts` (NEW)

**Scope:** Server Actions for admin path management (create, update, delete, add/remove/reorder courses) and a data-fetching helper for the learner view.

**Work:**
1. Types in `src/types/learning-path.ts`:
   - `LearningPath`: id, org_id, title, description, is_published, cover_image_url, created_at, updated_at
   - `LearningPathCourse`: id, path_id, course_id, sort_order; with nested `course: { id, title, description, status }`
   - `LearningPathWithProgress`: extends `LearningPath` with `courses: LearningPathCourse[]` + `completedCount: number` + `totalCount: number`
2. `createLearningPath(data)` — validates title, asserts admin/manager, inserts with `current_user_org_id()`-scoped client, returns the new path.
3. `updateLearningPath(pathId, data)` — asserts admin/manager + org ownership, updates title/description/is_published/cover_image_url, revalidates.
4. `deleteLearningPath(pathId)` — asserts admin/manager + org ownership, deletes (cascades to `learning_path_courses`), revalidates.
5. `addCourseToPath(pathId, courseId)` — asserts admin/manager, verifies course `status = 'published'` and belongs to the same org, inserts with `sort_order = MAX(sort_order) + 1`, revalidates.
6. `removeCourseFromPath(pathId, courseId)` — asserts admin/manager + org ownership, deletes the row, revalidates.
7. `reorderPathCourses(pathId, orderedCourseIds: string[])` — asserts admin/manager + org ownership, updates `sort_order` for each course_id in the list (1-indexed), validates all IDs belong to that path, revalidates.
8. `getLearningPathsForLearner(orgId)` — server-side data-fetcher (not a Server Action — used by Server Components); returns published paths with their courses (published only) and the learner's `completedCount` derived from `course_certificates`.

**Security:** All mutations use `assertOrgAdminOrPlatformAdmin` (or inline equivalent checking `current_user_role()`). `getLearningPathsForLearner` uses the authenticated Supabase client (user-scoped) — RLS is the security boundary.
