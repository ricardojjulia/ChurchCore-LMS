# COUNCIL-2026-026 — Automated Enrollment on Registration

**Date:** 2026-09-19
**Status:** Ratified
**Author:** Platform review (context: Council Review 3, Agent 4 — `docs/reviews/2026-09-19-council-review-3-synthesis.md` — ranked this the #1 competitive gap: "the most broken end-user flow for church adoption")

---

## Context

A new student who joins via `/join/[slug]` lands on a completely empty `/dashboard` with no course access and must be manually enrolled by an admin afterward. There is no self-serve path from "I joined my church's LMS" to "I can see a course." For a church running an uncoached pilot, this reads as broken software, not a missing convenience feature.

While investigating the fix, a second, independent, currently-live defect was found and verified directly against a running Postgres instance (schema + trigger inspection, not just migration-file reading): `enrollSelf()` in `src/app/actions/learning.ts` inserts into `enrollments` without setting `org_id`. The column is `NOT NULL` with no `DEFAULT`, and the only trigger on the table (`trg_refresh_perf_on_enrollment`) fires `AFTER INSERT/UPDATE`, not before — nothing stamps the column. Every real call to `enrollSelf()` against a live database throws a NOT NULL constraint violation. This was invisible because `learning.test.ts` fully mocks the Supabase client (a Proxy-based mock that cannot enforce real column constraints) and no e2e test exercises `enrollSelf()` against a real database. Self-enrollment for existing students has been silently broken by this bug independent of the registration-flow gap this council session set out to close.

---

## Decisions

**D1:** Fix the `org_id` bug at the schema layer, not the call-site layer. Add a `stamp_enrollment_org_id()` `BEFORE INSERT` trigger on `enrollments` that fills `org_id` from the enrolling profile's `profile_roles.org_id` whenever the inserted row's `org_id` is null. This closes the bug for every current and future insert path (session-bound, service-client, this feature's new path) by construction, rather than relying on each call site to remember to set it. The trigger only fills a null — it never overrides a caller-supplied value, so the existing RLS `WITH CHECK (current_user_org_id() = org_id)` semantics on the authenticated path are unchanged.

**D2:** Extract the enrollment-gating logic shared by both the existing self-enroll path and the new registration path into `src/lib/enrollment-core.ts` (`enrollCore()`), rather than duplicating the `enrollment_type` / prerequisite / age / level checks in the join flow. `enrollSelf()` becomes a thin session-bound wrapper over `enrollCore()`. This is a refactor of existing logic, not new gating rules — a parity test (`enroll-self-parity.test.ts`) confirms `enrollSelf()`'s observable behavior is unchanged after the extraction.

**D3:** Per-org configuration, not a hardcoded default course. Reuse the existing `organizations.settings` JSONB pattern (already used for branding/features/onboarding/demo) rather than a new table — add `auto_enroll_courses: string[]`, capped at 10 course IDs. An org admin opts a course in explicitly via a new `AutoEnrollSection` in `/admin/settings`; nothing is auto-enrolled by default for an org that hasn't configured it.

**D4:** Auto-enrollment in `verifyAndEnroll()` (`src/app/join/actions.ts`) runs after user creation and after the existing tenant-active re-check, and is best-effort per course: a gated course (invite-only, prerequisite unmet, age/level mismatch) is silently skipped via `enrollCore()`'s `SkipReason`, never blocks account creation, and never surfaces a gating failure as a registration error to the new user.

**D5:** Respect the existing `course_sections.enrollment_type` model (`open` / `cohort_gated` / `invite_only`) from the ministry-scenario work rather than introducing a second, competing enrollment concept. `auto_enroll_courses` is just a per-org list of course IDs fed through the same `enrollCore()` gate everything else already goes through.

## Prompt A — Migration: org_id stamping trigger + auto_enroll_courses settings key

**Files:**
- `supabase/migrations/20260919120000_auto_enroll_courses_settings.sql` (NEW)

**Scope:** One migration, two independent pieces: (1) the `stamp_enrollment_org_id()` `BEFORE INSERT` trigger fixing the live `org_id` bug on `enrollments`; (2) documentation-only support for the new `organizations.settings.auto_enroll_courses` JSONB key (no schema change needed — it's an existing JSONB column — but the migration file records the contract via a comment and, if the repo's convention requires it for JSONB sub-keys, a CHECK constraint capping the array to 10 entries).

**Work:**
1. `CREATE OR REPLACE FUNCTION public.stamp_enrollment_org_id() RETURNS trigger` — `SECURITY INVOKER` (not DEFINER — this must run under the inserting role's own RLS context, per CLAUDE.md Security Rule 1), looks up `org_id` from `profile_roles` for `NEW.user_id` when `NEW.org_id IS NULL`, sets it, returns `NEW`.
2. `CREATE TRIGGER trg_stamp_enrollment_org_id BEFORE INSERT ON public.enrollments FOR EACH ROW EXECUTE FUNCTION public.stamp_enrollment_org_id();`
3. Comment documenting the `auto_enroll_courses` JSONB contract on `organizations.settings`.

**Security:** Trigger must be `SECURITY INVOKER` so it cannot be used to write cross-tenant rows — it only ever derives `org_id` from the *inserting user's own* `profile_roles` row, which RLS already scopes correctly.

**Verification:**
- `npm run typecheck`
- Direct psql check: insert a row omitting `org_id` as a real authenticated role and confirm it now succeeds with the correct `org_id` populated (this is the regression test for the bug this prompt fixes).

## Prompt B — Backend: enrollCore extraction + auto-enroll wiring + org-settings actions

**Files:**
- `src/lib/enrollment-core.ts` (NEW)
- `src/app/actions/learning.ts` (MODIFIED — `enrollSelf()` refactored to call `enrollCore()`)
- `src/app/join/actions.ts` (MODIFIED — `verifyAndEnroll()` gains the auto-enroll loop)
- `src/app/actions/org-settings.ts` (MODIFIED — `assertOrgAdminOrPlatformAdmin()`, `getAutoEnrollCourses()`, `addAutoEnrollCourse()`, `removeAutoEnrollCourse()`)

**Scope:** Extract the existing gating logic into a shared, session-agnostic function; call it from both the refactored `enrollSelf()` and the new registration-time loop; add org-settings CRUD for the new list.

**Work:**
1. `enrollCore(params: EnrollCoreParams): Promise<EnrollCoreResult>` in `enrollment-core.ts` — takes an explicit Supabase client (session-bound or service), `uid`, `orgId`, `courseId`, optional `sectionId`; runs the existing `enrollment_type` / prerequisite / age / level checks; returns a discriminated result including `SkipReason` for a gated course rather than throwing.
2. `enrollSelf()` becomes a thin wrapper: resolve session + profile, call `enrollCore()`, translate the result to its existing return shape — no behavior change for the caller.
3. `verifyAndEnroll()`: after user creation and the tenant-active re-check, read `organizations.settings.auto_enroll_courses` (service client, capped read of first 10 entries even if more are somehow present), call `enrollCore()` per course with the service client, swallow `SkipReason` results, never fail registration on an enrollment error.
4. `org-settings.ts`: `assertOrgAdminOrPlatformAdmin()` guard (mirrors the existing `assertPlatformAdmin()` shape); `getAutoEnrollCourses()` / `addAutoEnrollCourse()` / `removeAutoEnrollCourse()` read-modify-write `organizations.settings` with the 10-entry cap enforced in code.

**Security:** `org-settings.ts` actions must reject a caller whose `current_user_org_id()` doesn't match the target org (unless `is_platform_admin()`) — an org admin may only edit their own org's `auto_enroll_courses`. The auto-enroll loop in `verifyAndEnroll()` uses the service client (no session exists yet at that point in registration) and must pass the *new user's* `orgId`/`uid` explicitly into `enrollCore()`, never infer it from an ambient session.

**Verification:**
- `npm run typecheck`
- `npm test` (existing `learning.test.ts` must still pass unmodified against the refactored `enrollSelf()`)

## Prompt C — Frontend: AutoEnrollSection admin UI

**Files:**
- `src/app/admin/settings/AutoEnrollSection.tsx` (NEW)
- `src/app/admin/settings/page.tsx` (MODIFIED — renders the new section)

**Scope:** A settings section listing the org's published courses with a toggle/checkbox for "enroll new joiners automatically," backed by `getAutoEnrollCourses()` / `addAutoEnrollCourse()` / `removeAutoEnrollCourse()`.

**Work:**
1. Server-fetch current `auto_enroll_courses` + the org's course list in `page.tsx`, pass down as props (per `CLAUDE.md` file conventions — no client-side data fetching in this component beyond the mutation calls).
2. `AutoEnrollSection.tsx` (Client Component): checkbox per course, calls `addAutoEnrollCourse`/`removeAutoEnrollCourse` Server Actions on toggle, optimistic UI with rollback on error, 10-course cap surfaced as a disabled state once reached.

**Security:** No direct Supabase calls from this Client Component — all writes go through the Server Actions in `org-settings.ts`, which enforce `assertOrgAdminOrPlatformAdmin()`.

**Verification:**
- `npm run typecheck`
- `npm run lint`

## Prompt D — Tests

**Files:**
- `src/tests/unit/enrollment-core.test.ts` (NEW)
- `src/tests/unit/org-settings-auto-enroll.test.ts` (NEW)
- `src/tests/unit/enroll-self-parity.test.ts` (NEW)
- `src/tests/e2e/auto-enroll.test.ts` (NEW, real Supabase)
- `src/tests/e2e/auto-enroll-admin.test.ts` (NEW, real Supabase)

**Scope:** Cover the extraction, the new settings CRUD, registration-time auto-enrollment, and — specifically because a mocked test suite is what let the `org_id` bug go undetected — a real-database regression test for the bug fix itself.

**Work:**
1. `enrollment-core.test.ts` — each gate (`open` succeeds, `cohort_gated` without membership returns `SkipReason`, `invite_only` without invite returns `SkipReason`, prerequisite/age/level unmet each return the correct `SkipReason`).
2. `enroll-self-parity.test.ts` — `enrollSelf()`'s observable return shape and error behavior are byte-for-byte unchanged pre/post refactor for both the success and each gated case.
3. `org-settings-auto-enroll.test.ts` — cap enforcement at 10, cross-org write rejected for a non-platform-admin org admin of a different org, platform admin can edit any org.
4. `auto-enroll.test.ts` (e2e, real Supabase, seeded UUIDs) — **the regression test for the bug**: join a fresh org configured with one `open` auto-enroll course, assert the new user has a real `enrollments` row with the correct `org_id` populated (this must fail against the pre-trigger schema and pass after Prompt A); also assert a `cohort_gated` auto-enroll course is skipped without failing registration.
5. `auto-enroll-admin.test.ts` (e2e) — full round-trip through the Server Actions: add a course, confirm it appears in a subsequent join, remove it, confirm it no longer does.

**Security:** Test 3's cross-org rejection must be exercised from the actual denied caller's client/session, not asserted as an intended policy.

**Verification:**
- `npm run test:ci`
- `npm run test:e2e`
