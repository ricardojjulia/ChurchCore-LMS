# ADR-2026-010: Guardian Notification Delivery Gets a Retry/Dead-Letter Pattern

**Date:** 2026-09-19
**Status:** ACCEPTED
**Deciders:** Architecture Council (Council Review 3)
**Tags:** reliability, guardian-portal, notifications, resend

## Context

Council Review 3 found three independent agents converging on the same weak point without coordinating: the state audit found `guardian_notification_queue` has a `status` enum (`pending`/`sent`/`failed`) but no retry, TTL, or dead-letter handling; the UX audit found `/guardian` has neither a `loading.tsx` nor an `error.tsx`; the feature audit found the guardian workflow's Resend delivery pipeline is "architecturally present but requires runtime verification" and flagged it as one of three things blocking closed-beta readiness.

Today, a failed guardian notification (grade posted, Resend temporarily down, transient DB error) is marked `failed` and never retried, with no monitoring query surfacing it. A guardian is silently never told their child received a grade. This is the single highest-confidence finding across the whole review — not because any one symptom is severe, but because three unrelated audits (data, UX, product) each independently traced back to the same root cause from a different angle.

## Decision

`guardian_notification_queue` processing gets a bounded retry with backoff and an explicit dead-letter state, visible to platform/org admins, rather than a silent terminal `failed` status. Concretely:

1. Add `attempt_count integer NOT NULL DEFAULT 0` and `next_retry_at timestamptz` to `guardian_notification_queue`.
2. The delivery job (wherever `/api/digest` or its cron currently marks a row `failed`) retries up to 3 times with exponential backoff before marking a row `dead_letter` instead of `failed`.
3. `dead_letter` rows are queryable by org/platform admins (a small addition to an existing admin view, not a new page) so a stuck notification is visible, not silent.
4. `/guardian` gains a `loading.tsx` and `error.tsx` matching the pattern already used by `/(reports)` and `/admin`, since a guardian hitting a transient failure today sees a raw framework error page instead of a friendly one.

## Consequences

- Guardians get a real reliability guarantee for grade notifications instead of a best-effort fire-and-forget queue.
- Admins get visibility into delivery failures instead of them being invisible until a guardian complains.
- This does not require verifying the Resend integration itself works end-to-end — that's an operational runtime check (Agent 4's closed-beta bar item #1), separate from this architectural fix, and out of scope for this ADR.
- No new table, no new RLS surface — `guardian_notification_queue`'s existing RLS continues to apply to the two new columns.
