# ADR-2026-011: Release Pipeline Runs Without a Staging Environment

**Date:** 2026-09-23
**Status:** ACCEPTED
**Deciders:** Ricardo Julia (project owner)
**Tags:** release, ci-cd, supabase, governance

## Context

`release.yml` ran a `deploy-staging` job (migrations + Edge Functions against a pinned staging Supabase project) before the production job. `docs/CODE-FACTORY-SYSTEM-PROMPT.md` §7.5 required staging and production to be separate, fully isolated instances.

In practice there is no staging environment for ChurchCore LMS. The pinned staging reference (`gytbfezrfrpsltdyfdgj`, recorded by the 2026-09-15 `release-staging-configuration-fix` automation run) is not an LMS project the owner controls. The staging job could never link to it: first with `Unauthorized`, then — once a valid personal access token was configured on 2026-09-23 — with `Missing required permission(s): project_admin_read`. Because the production job depended on staging, only 2 of the last 40 release runs succeeded, and nothing merged from PR #21 onward reached production (migrations, Edge Functions, or the Vercel deploy, since automatic Git deployment from `main` is disabled).

Keeping a foreign project reference in the release path is also a hazard: had the token ever been granted access to it, the release would have pushed LMS migrations into another project's database.

## Decision

1. Remove the `deploy-staging` job. `deploy` (production) now `needs: ci` directly.
2. The `production` GitHub environment's required-reviewer approval is the pre-deploy gate. CI — lint, typecheck, unit tests, build, and E2E against a disposable local Supabase stack — remains the pre-merge and pre-deploy check.
3. The `staging` GitHub environment and its `STAGING_SUPABASE_PROJECT_REF` / `SUPABASE_ACCESS_TOKEN` secrets are no longer used and can be deleted.
4. The isolation rule stays in force for the future: if a staging environment is added, it must be a separate, fully isolated Supabase project (or Supabase branching), introduced through its own council/ADR.

## Consequences

- Releases can succeed again with only production credentials; the backlog since PR #21 ships on the next approved release.
- Migrations are first applied to a hosted database in production. Mitigations: migrations are already exercised by the E2E suite's local Supabase stack in CI; the reviewer approving the production deployment should read any new files under `supabase/migrations/` before approving; migrations should stay forward-only and idempotent where practical.
- There is no hosted environment to smoke-test Edge Functions before production. Vercel preview deployments still exist for the frontend on every PR.
- Revisit when the pilot grows or a migration causes a production incident.
